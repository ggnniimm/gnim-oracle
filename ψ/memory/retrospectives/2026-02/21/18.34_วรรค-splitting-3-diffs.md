## Honest Feedback

Three friction points:

**1. Background task timing chaos.** Three tasks from a previous session context completed during this one, each potentially overwriting cache we'd just fixed. The order was unpredictable — `--cleanup` (7 sections), `--resplit` (18 sections), `--resplit` (175 sections). Any of these could have been a disaster. Fortunately they all held, but the design of `--resplit` touching ALL sections (not just the ones that changed) is genuinely dangerous. There's no "safe" mode that only resplits sections that haven't been manually patched. This needs a `--section` flag or a "locked" annotation in the JSON.

**2. Under-split discovery is expensive.** I had to read the full text of 15 sections across two large JSON files, manually identify paragraph boundaries in Thai legal text, and write split scripts with Unicode-sensitive string matching. It worked, but it required careful human judgment on every case. The tooling offers no structural help here — there's no "show me where this section's text has paragraph-like breaks that aren't in the parsed paragraphs" affordance.

**3. OCR quality ceiling.** Three diffs are permanently unfixable from this side. The law has paragraphs that weren't captured in the PDF OCR. The Excel says 2 or 3 วรรค, the text only shows 1. Short of manually typing in the missing paragraphs from the official law text, there's no path forward. The system should probably flag these as "known OCR gaps" rather than treating them as parser failures.

## Lessons Learned

- **Under-splits need manual text inspection, not rule tweaks**: When Gemini merges what should be separate วรรค, the fix is always a JSON cache patch with exact string matching, not a regex rule change. The rules can't help here because the text structure is correct — the problem is semantic.
- **`has_blank_sep` is a strong structural signal**: blank lines between a short non-legal line and the previous content are nearly always OCR artifacts from section headings spilling into the previous section's text.
- **Test with multiple Gemini resplits before calling done**: if the result holds through 3 resplits touching 100+ sections each, the rule-based framework is genuinely robust.
- **OCR truncation is a hard ceiling**: when expected > got and the section text simply doesn't have the content, document it and move on.
