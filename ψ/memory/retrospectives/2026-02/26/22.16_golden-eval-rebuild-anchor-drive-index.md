## AI Diary

This session taught me something about the gap between "correct" and "testable." When Ming asked me to add "ผ่านหัวหน้าเจ้าหน้าที่" to TC-003's must_contain, the phrase was legally correct — กวจ. 38381 explicitly says "รายงานผลให้หัวหน้าหน่วยงาน โดยผ่านหัวหน้าเจ้าหน้าที่" — but the LLM only included it sometimes. Three runs: fail, pass, fail. The legal truth doesn't automatically become retrieval truth.

The pattern I keep relearning: when a phrase is factually correct but non-deterministic in the answer, the fix isn't to lower the test bar — it's to raise the retrieval ceiling. Move the phrase into the anchor, increase its embedding similarity, make it structurally unavoidable. This is the anchor-as-guarantee pattern: not just "help the LLM find the right doc" but "make the right phrase appear in the right position so the LLM repeats it."

What pleased me today was the paraphrase test. "ครบกำหนดแล้วเสร็จตรงกับวันหยุด" and "สิ้นสุดสัญญาตรงกันวันหยุด" both pulled กวจ. 51349 as rank #1. The embedding space treats these as semantically equivalent even though the surface forms differ. That's retrieval robustness — the system is finding meaning, not matching keywords.

The 20140 index was satisfying in a different way. User says "เพิ่งเพิ่มเข้าไปใน Google Drive" — twelve seconds later we've found it in the CGD folder, classified it as Ruling_Committee at 95% confidence, chunked it into 15 pieces, embedded and stored. ## Honest Feedback

**Friction point 1: FAISS chunk accumulation on anchor edits.** Each time we ran `index_md_folder` after editing the anchor, it added 1 new chunk (content-hash dedup creates a new entry for changed text). The old chunk stayed. So after two anchor iterations, the index contained 3 versions of the anchor. The rebuild_faiss_index script re-embeds everything in metadata.pkl including the stale versions. This means the "clean" anchor is in the index but so are the old ones. Tests pass because any version with "ผ่านหัวหน้าเจ้าหน้าที่" satisfies must_contain — but it's architecturally messy. The right fix would be a "replace chunk" operation or a full rebuild after every anchor change, not incremental indexing.

**Friction point 2: must_contain stability testing requires 5+ runs.** We ran 3 runs to check "วันทำการถัดไป" — 2 passed, 1 failed. Then ran 3 more after changing to "วันทำการ" — all passed. But 3 runs isn't statistically meaningful. I ran 5 runs for TC-003 stability but that's still a small sample. The right answer is a larger stability test (10+ runs) for any phrase that failed even once. We don't have that infrastructure yet — run_eval.py doesn't have a `--repeat N` mode.

**Friction point 3: anchor text design is intuitive not principled.** The question "should 'ผ่านหัวหน้าเจ้าหน้าที่' go in (1) or (2)?" was decided by user intuition. And the user was right — moving it to (2) with "โดยผ่านหัวหน้าเจ้าหน้าที่" is semantically cleaner. But we have no formal principle for this. When anchor text gets longer (3+ facts to embed), the structural decisions become harder and more consequential. We need a design pattern: how long can an anchor be? How many facts can it carry? When does an anchor need to be split into two sections?

## Lessons Learned

1. **Non-deterministic phrases → anchor first, test second.** If a legally correct phrase fails must_contain even once, don't lower the bar. Update the retrieval anchor to guarantee the phrase, then re-test. The anchor is the contract between the document and the retrieval system.

2. **Paraphrase robustness is a free test.** Running the same question with different surface forms (ครบกำหนด vs สิ้นสุดสัญญา) reveals whether the system is matching semantics or keywords. If both pull the same source, the embedding is working correctly. Add paraphrase variants to golden test queries when coverage matters.

3. **batch_index dedup handles "just added to Drive" cleanly.** Running batch_index on an entire folder with dedup means new files get indexed automatically, existing files get skipped, and the caller doesn't need to know which files are new. The pattern is: index folder → dedup handles the rest. No need to track "which files were added since last run."
