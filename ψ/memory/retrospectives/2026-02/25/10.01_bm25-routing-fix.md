## AI Diary

There's something satisfying about tracing a bug all the way to its real cause instead of patching over it. I came into this session knowing the root cause from the previous context summary — the patch scripts had set `bm25._docs` instead of `bm25._corpus`. That part was quick to fix: 10 minutes, confirmed, BM25 search for "5529" returning scores 8.31–10.82. Done, right?

Not quite.

The moment I ran end-to-end through the full pipeline, กวจ 5529 was still missing from the top 5. That was the more interesting bug — a structural imbalance in the reranker's normalization. Both BM25 and FAISS normalize their best result to 1.0, then apply weights. FAISS weight 1.0, BM25 weight 0.9 (or 0.7 as actually hardcoded — there was even a config mismatch I found along the way). So BM25 can never win. Even with a perfect exact match at score 10.82, it gets multiplied down below FAISS's ceiling.

The hardest part was thinking through the right fix. I could raise BM25 weight globally, but that would make BM25's top result (even for poor keyword matches) beat FAISS on semantic queries. That's wrong in the other direction. The insight was that doc-number queries are a fundamentally different type of search: FAISS doesn't understand that "5529" means a specific document — it returns semantically similar procurement letters (which is all ข้อหารือ). BM25 understands it precisely because "5529" is a token that appears exactly in the metadata prefix.

The routing solution — detect `\d{4,}` in the query, skip FAISS entirely, return only BM25 — feels correct. Clean. The two search modalities have different strengths and the system should route between them, not try to blend them in every case.

What I keep noticing across this whole re-indexing week: each fix reveals the next layer. Thai numerals → Arabic normalization → BM25 tokenizer splits "/" differently → bare suffix as separate field → wrong attribute in patch script → normalization asymmetry → missing routing logic. Every fix was correct, but incomplete because the next constraint wasn't visible yet. That's what makes this kind of work interesting. The bugs aren't random — they're systematic consequences of design choices compounding.

## Honest Feedback

Three friction points this session:

**1. Context compaction loses critical in-flight state.** Coming back from a compacted context, I had to trust the summary about which attribute was wrong (`_docs` vs `_corpus`). The summary was accurate, but if it had been slightly off, I'd have wasted time re-tracing. Multi-session debugging of state-heavy systems (BM25 corpus, FAISS vectors, metadata.pkl) is hard when the state is only in memory. The lesson is: when a patch session involves multiple in-memory objects, write the exact fix as a standalone script that can be re-run, not as one-off REPL commands that are only in the transcript.

**2. The config/code mismatch was a quiet defect.** `BM25_WEIGHT = 0.9` in config.py, `"bm25": 0.7` in reranker.py — two files telling different stories. This only became visible because I was reading both carefully while debugging. In production codebases this kind of drift is common and dangerous. The fix (import from config) is correct, but the fact it existed for this long means tests don't cover weight consistency. A simple assertion or at least a comment linking the two files would prevent this.

**3. Iterative API spelunking adds friction.** To run end-to-end tests, I had to discover `IndexManager`, `Retriever`, `retrieve_async`, `rerank`'s actual signatures — not what I remembered from the summary. Three failed attempts before I got the right call sequence. This is a developer experience issue: there's no quick-reference in the project for "here's how to run a single query through the full pipeline." A `scripts/test_query.py` that wires everything up and takes a query as CLI arg would pay for itself in 10 minutes.

## Lessons Learned

1. `BM25Store._rebuild()` uses `self._corpus` (list of tokenized lists), not `self._docs` or anything else. Patch scripts must set `_corpus` correctly.
2. Normalization asymmetry in rerankers: when different sources normalize to [0,1] and then apply weight, the source with highest weight always wins ties — even if the lower-weight source has a perfect match.
3. Semantic search (FAISS) and exact-match search (BM25) have fundamentally different strengths; routing between them by query type beats trying to blend them with weights alone.
