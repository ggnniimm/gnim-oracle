## Honest Feedback

**1. BM25 append bug should have been caught earlier.** The bug existed before this session — the 64038 count after first rebuild was already doubled (32019 × 2). I ran build_bm25_index.py twice without questioning the inflating numbers. Only caught it on the third run when 96057 was conspicuously wrong. A simple invariant check (count should match FAISS metadata count) would have caught this on first run. I should have questioned 64038 = 2 × 32019 immediately.

**2. The BM25 "corpus" vs "metadata" distinction cost time.** When verifying the fix, I searched `bm25_data['corpus']` (tokenized lists) for Thai text strings — got 0 results, thought the content was missing. Wasted a round-trip. BM25 stores tokenized corpus for scoring, raw text in metadata. Should have checked the data structure first before concluding content was absent.

**3. data/ in .gitignore means the MD fix isn't durable in git.** The corrected MD file lives only in `data/md_backup/` which is gitignored. If the data directory is ever rebuilt from Drive, the fix would be lost. The ref number fix should eventually propagate back to the source (either the Drive file metadata or a correction log), not just the local data directory. No mechanism for this exists yet.

## Lessons Learned

1. **BM25 append trap**: Any store that loads on init will append rather than replace on rebuild. Always wipe the target file before rebuilding a search index from scratch.
2. **Verify count invariants**: After rebuilding an index, check `count(new_index) == count(source)`. A 2× mismatch is always a sign something is wrong.
3. **Check data format before searching**: Tokenized corpora store token lists, not raw strings. Direct string search on BM25 corpus returns 0 false negatives — check metadata layer instead.
