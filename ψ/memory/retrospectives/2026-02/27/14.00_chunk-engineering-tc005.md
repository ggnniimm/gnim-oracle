## AI Diary

This session felt like a breakthrough in understanding. Not the kind where you discover something new, but the kind where scattered observations click into a unified pattern.

The anchor-LLM tension I documented yesterday? Today I lived it again with ว124. First attempt: a full sentence about "เมื่อลงนามในสัญญาแล้ว คณะกรรมการตรวจรับพัสดุจะต้องดำเนินการบริหารสัญญา" — beautiful for LLM comprehension, terrible for retrieval (sim 0.7550, buried in results). Strip it to keywords: "หน้าที่คณะกรรมการตรวจรับพัสดุเริ่มต้นเมื่อลงนามสัญญา บริหารสัญญา เร่งรัด ติดตาม ประเมินผล" — sim jumped to 0.7980, rank 3 in FAISS. The pattern is consistent and predictable now.

But the 20140 chunk engineering was the more interesting discovery. Ming asked: "20140 isn't really about duties, but if we want the answer to include it as a duty, what do we do?" Three options presented. Ming chose chunk engineering — modifying the source text rather than the prompt. And it worked beautifully. By adding "มีหน้าที่เสนอความเห็น" as positive framing, the LLM now categorizes the same content as an additional duty instead of a limitation. Same document. Same retrieval. Different interpretation — steered by a single sentence.

This is the power and the danger of chunk engineering. We're not changing what the law says. We're changing how the summary presents it. The original document text is untouched. But the search summary — which exists purely for retrieval and context — shapes the LLM's framing. It's editorial, not legal. Ming understands this distinction, and that's what makes it responsible.

The session also revealed something about my own error patterns: when asked to run queries directly, I stumbled through import errors and API mismatches for several minutes before finding the right incantation. The eval pipeline (`run_eval.py --id TC-XXX --json`) is the right tool. I should stop trying to bypass it.

## Honest Feedback

**Friction 1: Context compaction lost critical details.** The session started from a compacted context, and I had to reconstruct what TC-003's current state was, what changes had been made to which files, and what the eval pipeline commands were. The summary was good but I still fumbled on specifics like `--id` vs `--tc` flags. This is a recurring problem — compaction preserves strategy but loses syntax.

**Friction 2: Direct query attempts wasted time.** I tried multiple times to run queries directly through Python imports (FAISSStore, Retriever, IndexManager) before remembering that `run_eval.py --json` gives the full answer. Each failed attempt required debugging import paths, parameter names, and module dependencies. The eval pipeline exists precisely to avoid this. I need to internalize: use the pipeline, not raw imports.

**Friction 3: Anchor iteration is manual and slow.** Testing anchor sim scores requires: (1) edit MD file, (2) rebuild index chunk, (3) run query, (4) check sim score in output. Each cycle takes 2-3 minutes. A dedicated anchor testing tool — input candidate text, output sim score against a query — would cut iteration time dramatically. This is the third session where anchor tuning consumed significant time.

## Lessons Learned

1. **Chunk engineering works**: Modifying บทสรุปสำหรับสืบค้น sections with keyword anchors + positive-framing sentences can change LLM interpretation without breaking retrieval
2. **Keyword density is king for retrieval**: Even 2 extra words can drop sim significantly; for anchors competing against strong titles, every word counts
3. **Use the eval pipeline**: `run_eval.py --id TC-XXX --json` is the right tool; stop trying to bypass it with raw imports
