## AI Diary

วันนี้ผมเจอ tension ที่ฝังลึกอยู่ใน RAG architecture มาตลอด และวันนี้เห็นมันด้วยตาตัวเอง

เริ่มต้นด้วย question ที่ดูเหมือนง่าย: ทำยังไงให้ anchor beat title สำหรับทุก query variant ที่ user อาจพิมพ์มา ผมทดสอบ isolation → ได้ 6/6 wins ด้วย cx5 ดูดีมาก แต่แล้วพบว่า isolation test ไม่ตรงความจริง — actual chunk มี metadata header นำหน้า การทดสอบใหม่กับ full format ให้ผลต่างกันมาก cx5 ยังชนะ 5/5 แต่ margin บางลง

ตอนนี้ดูเหมือนทุกอย่าง on track: cx5 ถูก retrieve ที่ rank [4], score 0.9998, cited เป็น [4] ใน answer แต่ "แผน" ไม่ปรากฏใน answer เลย

นั่นแหละคือ moment ที่ผมเข้าใจจริงๆ ว่า retrieval ≠ generation. การที่ chunk ถูก retrieve ไม่ได้การันตีว่า LLM จะ synthesize content ออกมา chunk ที่เป็น headline keyword list ("เสนอความเห็น แผน หน้าที่ ขอบเขต") ถูก LLM cite เป็น [4] แต่ไม่มีเนื้อหาพอให้ LLM สร้างประโยค "แผน" ขึ้นมา

ผมลอง approach ต่อมา: ทำ anchor text เป็นประโยคที่สมบูรณ์กว่า เช่น "อำนาจหน้าที่คณะกรรมการตรวจรับพัสดุ กรณีสัญญากำหนดแผนการดำเนินงาน มีหน้าที่เสนอความเห็น ไม่มีอำนาจตัดสินใจ" — ผลคือ retrieval score ตกทันที เพราะ long text dilutes embedding away from query keywords แค่เพิ่ม "การดำเนินงาน" สองคำก็ทำให้ drop จาก 5/5 เป็น 2/5

นี่คือ fundamental constraint ของ embedding model: ไม่มี anchor text เดียวที่ simultaneously (1) beats title chunk สำหรับ query variants ทั้งหมด AND (2) contains complete sentence ที่ LLM จะ reproduce เป็น "แผน"

การค้นพบนี้นำไปสู่ decision ที่ถูกต้อง: แยก TC-004 ออกมา query ที่ specific ตรงกับ 20140 โดยตรง พอ query เปลี่ยนเป็น "กรณีสัญญากำหนดให้ผู้รับจ้างเสนอแผนการดำเนินงาน..." ปรากฏว่า stale anchor v2 ที่เหลืออยู่ใน FAISS จากการทดลองเมื่อวาน กลับกลายเป็น perfect match — ได้ rank [1] และ LLM ผลิต "แผน" ออกมา stable 3/3 runs

บางทีสิ่งที่เราคิดว่า "stale" มันไม่ได้ stale — มันแค่รอ query ที่ถูกต้อง

## Honest Feedback

**Friction point 1: isolation test misleads** ผมทดสอบ anchor candidates ด้วย text ที่ไม่มี metadata header ตลอดช่วงแรก ได้ผล 6/6 win และ commit แผนไปแล้ว แต่เมื่อ test ด้วย actual FAISS stored vectors ผลต่างออกไป ถ้า test ด้วย actual stored text ตั้งแต่ต้น จะประหยัดเวลาได้ 20-30 นาที pattern เดิม: ต้องตรวจ sim ด้วย actual stored vectors เสมอ ไม่ใช่ compute ใหม่

**Friction point 2: anchor-LLM tension ไม่ถูก document ไว้ก่อน** ผมรู้ว่า embedding dilution เกิดขึ้นเมื่อเพิ่ม off-topic content (จาก session เมื่อวาน) แต่ไม่ได้ generalize ไปถึง "any meaningful sentence about แผน will dilute retrieval score" จนกว่าจะเจอ empirically วันนี้ ถ้า document ไว้ใน memory ว่า "anchor text และ LLM-generatable text มี semantic pull ต่างทิศกัน" ตั้งแต่ต้น จะไม่เสียเวลา try หลาย candidates

**Friction point 3: stale chunk accumulation** ตอนนี้ FAISS มี chunks 32733-32737 จาก anchor experiments หลายรอบ (v1, v2, cb, cx5, cx9) ทุก index_md_folder run เพิ่ม 1 chunk แต่ไม่ remove old ones ทำให้ index ใหญ่ขึ้นเรื่อยๆ โชคดีที่ stale chunks score ต่ำกว่า anchors ใหม่ แต่สะสมไป index เริ่ม noisy ต้องมี cleanup plan — rebuild FAISS จาก clean MD state

## Lessons Learned

1. **Isolation sim test ≠ actual FAISS sim** — ต้อง embed text พร้อม metadata header (format เดียวกับที่ index_md_folder สร้าง) ก่อน compare sim ไม่ใช่ embed content-only text
2. **Anchor-LLM tension เป็น fundamental constraint** — text ที่ win retrieval (short/dense/keyword) ≠ text ที่ LLM synthesize ออกมา (complete sentence) ไม่มี single anchor text ที่ทำได้ทั้งสอง เมื่อ document มี content-rich chunks อยู่แล้ว
3. **must_contain ต้องผ่าน phrasing stability test** — phrase ที่ปรากฏ 3/3 ใน manual test อาจ fail ใน run_eval.py ต้องทดสอบด้วย eval pipeline จริง ไม่ใช่แค่ manual query
4. **Stale chunks = archived experiments** — อย่า rebuild FAISS ทันทีหลัง experiment บางครั้ง stale chunk ที่ดูเหมือน "waste" อาจกลายเป็น perfect answer สำหรับ query อื่น
