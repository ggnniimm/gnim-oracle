## AI Diary

I started this session carrying the weight of 26 failures. The fix_truncated_ocr.py script had run and produced `OK: 1, FAIL: 26` — a crushing ratio. All 26 failures were HTTP 404 from Google Drive. My first instinct was to find a workaround: check the OCR cache, look for token files from the original account, see if file_urls were publicly accessible. One by one, each avenue closed. The cache had identical content to the MD files (of course — the MD *came from* the cache). No token files. The file_urls require the original Drive account.

Then I did what I should have done sooner: actually look at the files. Are they truncated? Do they end mid-sentence? The first file I checked — `001_กวจ_26242_270766` — ended with a proper สรุปข้อวินิจฉัย with bullet points. Then I ran a systematic check: all 26 files have complete สรุปข้อวินิจฉัย with bullet content. They're fine.

The relief was immediate, but so was the lesson. I had built an audit heuristic (ประเด็น count vs ข้อวินิจฉัย count) and trusted it too much. กวจ_0405.4_22315 was confirmed truncated by *looking at the actual text*, not by a count heuristic. The heuristic was useful for triage but not reliable as a gold standard.

What I did right: I verified before accepting the "26 files broken" conclusion. I checked the OCR cache, the file structure, and ultimately the actual content. That verification loop — hypothesis → check → revise — is the right pattern. What I did wrong: I built the audit script in a previous session and never questioned whether its heuristics were precise. False positives in a diagnostic tool waste a lot of effort.

The OAuth OOB fix was satisfying. Google deprecated `urn:ietf:wg:oauth:2.0:oob` in 2022 and our code still had it. `run_local_server(port=0)` is the modern way — opens browser, starts ephemeral server, catches the redirect automatically. Clean.

## Honest Feedback

**Friction point 1 — Audit heuristic precision**: The original audit script counted ประเด็นข้อหารือ occurrences vs numbered ข้อวินิจฉัย items. This was a reasonable proxy for truncation (more ประเด็น than answered items = possible truncation) but it wasn't validated against ground truth before scaling to 32 files. The กวจ_0405.4_22315 case should have prompted: "is this heuristic reliable on a sample before I trust it for 32 files?" We skipped that validation step.

**Friction point 2 — Drive account confusion**: The 26 files have file_ids from a Drive folder (`DRIVE_FOLDER_GVAJ`) that isn't in the current .env. This is a project configuration gap — the original OCR was presumably run with a different account, and there's no documentation of which account that was or how to recover access. When a system depends on external credentials, the "which account" question should be documented somewhere.

**Friction point 3 — Script ran before verification**: fix_truncated_ocr.py ran all 27 files (took ~55 minutes with sleep delays) before we confirmed whether the 26 files were actually broken. A better approach: spot-check 3-5 flagged files manually FIRST, then run the script only on confirmed-broken files. The script ran 26 files that turned out not to need fixing, wasting API quota and time.

## Lessons Learned

1. **Audit heuristics need ground-truth validation before scaling** — always spot-check 3-5 flagged items manually before running automated fixes on 30+
2. **Complete sections (สรุปข้อวินิจฉัย present) = not truncated** — if a document ends with a proper summary section, it's complete even if numbered items don't match expectations
3. **Google OAuth OOB is deprecated** — use `run_local_server(port=0)` for installed app flows
4. **Check what you have before fetching** — the cache/file comparison should have been step 1, not step 4
