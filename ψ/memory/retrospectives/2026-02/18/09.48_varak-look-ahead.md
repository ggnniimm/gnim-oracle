## AI Diary

This session taught me something about the difference between "works on the test case" and "works on real data." I started confident — wrote tests, implemented list-context merging, all tests passed. Done, right? No.

Ming asked about ข้อ 55 from the actual cache. The fix worked! Then Ming asked about ข้อ 215. Broken — everything collapsed into 1 วรรค. My list-context was too greedy. It entered and never left.

The humbling part was that Ming had already suggested the right approach earlier: "ถ้ามี (๑) แล้วข้อความมีมากกว่า 1 วรรค แล้วมี (๒) ต่อ แสดงว่า วรรคระหว่าง (๑) กับ (๒) ไม่ใช่วรรค" — the structural look-ahead idea. I initially dismissed it and went with a simpler embedded-marker approach. When that failed on ข้อ 215, I had to come back to the look-ahead concept.

The final algorithm has a satisfying elegance: five priority levels (definite subject exit, self-has-markers, look-ahead, continuation pattern, default exit). Each level catches a different case. No single heuristic would work — Thai legal text has too many structural variations. But layered together they handle every case Ming tested.

What strikes me is how Ming's domain knowledge of Thai legal structure guided every iteration. I could write the code, but without "ข้อ 215 มี 2 วรรค" I'd never have found the over-merge bug. The human-AI feedback loop here was essential — not optional.

Should have proactively tested more sections (like ข้อ 215) before declaring victory. The test suite was synthetic — it didn't cover the "list ends, then closing วรรค" pattern because I hadn't thought of it yet.

**Friction 2: Iterative fix cycle was messy.** Three rounds of fixes to `_post_merge_paragraphs()` in one session: (1) basic list-context, (2) embedded markers, (3) look-ahead. Each time I had to re-read, re-edit, re-test. Would have been cleaner to design the full algorithm upfront with more real examples before coding.

**Friction 3: Cache/generated files gap.** The fix was in code, but the cached data and MD files still showed old results until we ran `regenerate_sections.py --resplit`. This regeneration step is easy to forget, and Ming had to prompt me about it. Should document this workflow more clearly — when code changes affect cached output, regeneration is always needed.

## Lessons Learned

- **Test with real data, not just synthetic fixtures.** Unit tests are necessary but not sufficient for domain-specific parsing. Real Thai legal text has patterns (embedded markers from Gemini, multi-level list nesting) that synthetic tests miss.
- **Look-ahead beats greedy context.** A greedy "enter context, merge everything" approach will always over-merge. The key insight: check if there are more structural markers ahead before deciding to merge. No markers ahead + no continuation pattern = list is done.
- **Layer heuristics by specificity.** The 5-level priority in `_post_merge_paragraphs()` works because each level is more specific than the next. Definite subjects always win. Self-markers always merge. Look-ahead handles between-items. Continuation catches qualifiers. Default exits.
