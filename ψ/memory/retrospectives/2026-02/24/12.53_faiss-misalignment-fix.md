## AI Diary

This session had a clean diagnostic arc — each clue led directly to the next. The `list index out of range` crash was opaque from the CLI, but once I read `faiss_store.py` and saw `self._metadata[idx]`, the cause was obvious: the FAISS index has 15,019 vectors but metadata has 14,637 entries. The guard fix took one line.

But the more interesting discovery was *why* this happened. During the re-OCR cleanup from the previous session, we removed 375 entries from metadata.pkl by filtering — but FAISS has no delete API, so those vectors stayed. New chunks were then appended to both FAISS (at positions 14,466+) and metadata (at positions 14,091+). The result: FAISS position 14,106 holds an old orphan vector, but metadata[14,106] contains a ว 681 chunk. Completely misaligned. Any chunk indexed after the re-OCR cleanup was effectively invisible.

The rebuild was straightforward — re-embed 14,637 texts in batches of 100, build a fresh IndexFlatIP. ~45 minutes of API calls, perfectly clean result. Satisfying.

The retrieval quality issue was harder. ว 681 title chunk ranked #1 because its text "ระยะเวลาในการตรวจรับพัสดุ" matches the query semantically. But the content chunks ("งานจัดซื้อจัดจ้างที่มิใช่งานจ้างก่อสร้าง 5 วันทำการ") embed very differently from an abstract "how long" query. They were at FAISS rank 29-31, below any reasonable top-K cutoff.

The source injection solution feels right. It's a one-sided intervention: only triggers when rank-1 source appears exactly once (suggesting a title-without-content situation), and injects from the already-computed candidate pool with no additional API calls. Three extra chunks that the LLM receives as bonus context from the most relevant source.

Ming's question "ถ้าถามคำถามอื่น ก็ต้องมานั่งแก้แบบนี้อีกรึป่าว" was the right one to ask. The FAISS misalignment was a one-time corruption — won't recur unless we do another metadata-only cleanup without rebuilding. The retrieval quality tuning is a general improvement that benefits all queries, not just this one. That distinction matters: knowing when a fix is permanent vs when it's a symptom of something structural.

## Honest Feedback

**Friction 1: The misalignment was predictable.** The re-OCR cleanup from the previous session explicitly noted "FAISS has no delete API — bad chunks remain with empty metadata" in the retrospective. That's *exactly* the misalignment that happened. But I didn't anticipate that the NEW chunks added after the cleanup would also be misaligned — I only expected the orphan vectors to be harmless noise. In fact, the orphan positions shifted the metadata-vector correspondence for all subsequent inserts. This should have been caught immediately after the re-OCR — a simple alignment check (assert index.ntotal == len(metadata)) would have flagged it.

**Friction 2: Three rounds of config tuning before source injection.** I went: FAISS_TOP_K 10→20, then →40, then BM25_WEIGHT 0.7→0.9, then source injection. Each step was a hypothesis that seemed reasonable but wasn't sufficient alone. I should have profiled the candidate pool first — checked exactly where ว 681 chunks ranked in the merged pool before deciding what to tune. Instead I tuned blindly, saw "still not in top-15," then tuned again. Three rounds of iteration could have been one with better upfront analysis.

**Friction 3: BM25_WEIGHT change might have unintended effects.** Raising BM25_WEIGHT from 0.7 to 0.9 makes keyword matches nearly equal to semantic matches. For this query it helped. But for queries where BM25 retrieves false positives (documents that share keywords but aren't relevant), those false positives will now score higher. I didn't test this tradeoff on other queries — the change was made entirely based on one query's performance. A proper evaluation would test a set of queries before committing the change.

## Lessons Learned

1. **FAISS misalignment after metadata-only cleanup**: deleting from metadata.pkl without rebuilding FAISS corrupts alignment for ALL chunks added after the deletion, not just the deleted positions. After any metadata filter operation, always rebuild FAISS immediately.
2. **Assert alignment check**: add `assert index.ntotal == len(metadata)` after every rebuild/patch operation to catch misalignment early.
3. **Source injection pattern**: when title chunk ranks #1 but content chunks don't surface, inject sibling chunks from same source. Trigger: rank-1 source appears only once in top-K.
4. **Profile before tuning**: check exact ranks of target chunks in merged candidate pool before adjusting TOP_K or weights — prevents multiple rounds of blind tuning.
