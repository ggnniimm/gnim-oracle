That was wrong — I gave it without having the source document. The LLM at the time hedged and said something imprecise, and I filled in the gap with logic rather than evidence. That's the error.

When Ming asked directly "ตกลงคำตอบคืออะไร" this session, I read the actual 28 chunks from 5529 before answering. The answer to Ming's original query was กรณีที่ 2 — and the answer is "ได้" not "ไม่ได้."

The indexing workflow for 5529 worked smoothly. The `--retry-file` flag was the right tool — feed a single file ID, index only that file without re-scanning the whole folder. OCR correctly classified it as Ruling_Committee and auto-corrected the doc_number (OCR read '55', filename had '5529') and date (OCR read 2022-02-04, filename had 2022-02-08).

One persistent limitation surfaced again: queries by document number ("มีหนังสือเลข 5529...") don't work because the reference number lives in the filename, not in the document text. The retrieval system searches content, not metadata. This is by design but creates confusion when users want to verify "does document X exist in the index?" There's a gap here — a metadata search layer would help.

The "ครบกำหนดส่งมอบงานตรงกับวันหยุด" query was a clean win. Single authoritative source (กวจ. 51349) dominated the results, and the answer covered both สัญญาซื้อขาย and สัญญาจ้างทำของ cases with correct legal basis (ป.พ.พ. มาตรา 193/8).

## Honest Feedback

**Friction 1: Previous session gave a wrong legal answer without a source.** When Ming asked about "งดหรือลดค่าปรับ" in the earlier session, I answered "ไม่ได้" based on reasoning rather than reading the document. This is a pattern I need to watch: when retrieval returns chunks and LLM hedges, I tend to fill in the gap with my own legal interpretation. That's the wrong move for a system that's supposed to cite sources. The correct behavior: if the retrieved chunks don't definitively answer the question, say so — don't substitute my own judgment.

**Friction 2: "5529 ไม่พบ" from dry-run, but file was there.** The dry-run in the previous session found nothing in CGD/CGD2/CGD3, but the file was actually in CGD all along. The dry-run uses `list_pdfs()` which filters by PDF mimeType, which should have worked. I suspect the previous dry-run may have been on a different folder ID or had some issue. This session I used `list_files()` (which shows all files, not just PDFs) with a name filter — and found it immediately. Should have done that first rather than relying on dry-run output.

**Friction 3: Document number not searchable.** The field `doc_number` is stored in metadata but is `None` for 5529 (OCR returned '55' and was corrected from filename, but the metadata shows None). Even if it weren't None, BM25 and FAISS search text content, not metadata fields. So "มีหนังสือเลข 5529..." will never work as a content query. A proper fix would be to prepend metadata (doc_number, date, issuer) to the chunk text during indexing, so these become searchable. Or add a metadata-only search path in the retriever.

## Lessons Learned

1. **Don't fill gaps with reasoning**: When retrieval doesn't surface a clear answer, say "ไม่มีข้อมูลเพียงพอ" — don't substitute with own legal interpretation. Especially dangerous in Thai legal context where distinctions are precise.
2. **Use `list_files()` for file search, not dry-run**: `list_pdfs()` dry-run shows files the indexer would process, but `list_files()` + name filter is better for finding a specific file.
3. **Document number not in chunk text**: OCR extracts text from PDF pages — reference numbers often appear in the header/letterhead in a format OCR misreads (5529 → 55). Prepending metadata to chunk text during indexing would fix this.
