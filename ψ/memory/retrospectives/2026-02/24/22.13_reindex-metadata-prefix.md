## AI Diary

This session had a clear shape: one focused code change, then a long waiting game. The code change itself was small — `_metadata_prefix()` is maybe 10 lines — but the rationale was solid. Every circular document has a reference number (เลข กวจ. 5529, เลข กค. ว 196, etc.) that users will naturally query by. Without prepending that to chunk text, the retrieval system is blind to those identifiers. The fix is conceptually clean: enrich the text before indexing so BM25 can find it.

The re-index decision was harder than it looked. Once we added the prefix, the existing 14,665 vectors became inconsistent — indexed without the prefix, so doc numbers still invisible. The only clean fix was wipe and rebuild. I walked Ming through the implications clearly: which storage is real-time (dedup.db, OCR cache) vs. end-of-process (FAISS, BM25). That transparency mattered because Ming asked a good question mid-run: "can I stop now and continue tomorrow?" The answer was no — stopping mid-process would leave dedup.db out of sync with FAISS. Knowing the save semantics of each storage layer is exactly the kind of thing a human shouldn't have to think about but a system-aware partner should explain clearly.

The 2.5-hour wait for CGD3 was genuinely uncertain at first. CGD3 files weren't in OCR cache (previous indexing had used CGD3 but somehow didn't persist cache — unclear why). So every file needed a full Gemini round-trip: upload PDF, classify, upload again, extract. About 35-40 seconds per file × 183 files = the math was uncomfortable. But at 22:10 it completed cleanly: 180/183 indexed, 3 failed. The 3 failures are probably corrupt or empty PDFs — minor.

What I'm most satisfied about: the progress monitoring approach. When the TaskOutput buffer capped at 13/183 and FAISS was unreadable mid-run, I found dedup.db as a real-time proxy. 1,386 new chunks ÷ ~13 chunks/file = ~107 files. That's a useful pattern: when you can't read the destination (FAISS saves at end), read the real-time side channel (dedup.db). It's the same principle as reading a journal to track a long-running operation.

## Honest Feedback

**Friction 1: TaskOutput buffer caps early.** The background task output visible via TaskOutput stopped at 13/183 even though the process ran to completion. This means "check progress" requests are effectively blind after the first few files. The workaround (dedup.db as proxy) worked but required knowing the internals. A better approach would be writing progress to a sidecar file that can be read directly. Something like `echo "file_count" > data/progress.txt` after each file. Low cost, high visibility.

**Friction 2: CGD3 not in OCR cache — cause unknown.** CGD and CGD2 had their cache files intact after the wipe (we kept ocr_cache/). But CGD3 needed full re-OCR despite having been indexed before. I don't know why. Possibly the previous indexing session for CGD3 used a different THAI_RAG_DATA_DIR or the cache wasn't flushed before the earlier wipe. Worth checking `ocr_cache/` naming scheme to understand the ID-to-file mapping — if CGD3 had a naming collision or the folder ID wasn't preserved in the cache key.

**Friction 3: 3 failed files with no filename context.** The failed log has 3 Drive file IDs but no filenames. To retry, we'd need to look them up via Drive API to know what documents they are. The failed log format should include the filename alongside the ID — it's right there in `file_info["name"]` when the failure happens. A one-line fix: `failed.append(f"{file_id}  # {file_name}")`. Worth doing before the next batch session.

## Lessons Learned

1. **dedup.db as real-time progress proxy**: When FAISS saves only at end-of-process, check dedup.db (updated per-chunk) to estimate files indexed. `total - baseline / avg_chunks_per_file = files_done`.
2. **Save semantics matter for interruption planning**: FAISS/BM25 = save at end. dedup.db/OCR cache = real-time. Never stop a batch mid-run without understanding which state is preserved.
3. **Failed log should include filename**: `failed.append(file_id)` loses context. Should be `file_id  # filename` for human-readable retry planning.
