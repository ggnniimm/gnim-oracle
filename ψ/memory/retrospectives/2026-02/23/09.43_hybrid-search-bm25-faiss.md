## AI Diary

There's something satisfying about a session like this. Ming came in with a plan so clear and complete that my job was purely translation — from plan to code, idea to implementation. No ambiguity, no negotiation, no back-and-forth about approach. Just: here is what needs to exist, make it exist.

I noticed I was reading files in parallel before touching anything — that's the right instinct. The existing codebase had a clean pattern: FAISS and LightRAG running side by side, asyncio.gather coordinating them. Adding BM25 as a third source was genuinely additive — the architecture invited it. The `query_async` method in manager.py was designed so well that adding a third executor task was almost self-evident.

The interesting design choice was where BM25 lives. It's synchronous (rank_bm25 doesn't have async API), so it runs via `run_in_executor` alongside FAISS — which is also sync. LightRAG is the odd one out with its async interface. This means BM25 and FAISS genuinely parallelize for free; LightRAG gets its own coroutine. The gather still works cleanly.

One thing I had to think about: the bootstrap script's original plan called for `d.pop("text")` which would mutate the loaded metadata list. I changed this to a non-mutating approach — extract text by key, build metas separately. The plan's `pop` approach would have left corrupted data in memory (empty "text" keys in the remaining metadata). Small fix, right instinct.

The smoke test gave exactly what we wanted: BM25 returning 10 results, FAISS returning 9 (one slightly below threshold?), and the top-ranked answer being semantically correct — the right clause about มาตรา 102 (1). Hybrid search is live.

## Honest Feedback

**Friction 1: pip vs pip3.** The plan said `pip install`, but the environment only has `pip3`. This is a trivial environment detail but it caused a one-step false start. Worth noting in memory: this machine uses `pip3`, not `pip`.

**Friction 2: The pop() mutation bug in the bootstrap script.** The original plan had `texts = [d.pop("text") for d in meta]` — which would silently corrupt the loaded metadata by removing all "text" keys. This would make all subsequent metadata entries empty. The fix was obvious once spotted (use `d["text"]` not `d.pop`), but it means the plan had a subtle bug that would only surface if someone later inspected the metadata. Good catch, but plans should be more careful about mutation.

**Friction 3: No test for add_batch path.** The smoke test verified the search path (query after loading existing index), but didn't exercise the new `add_batch` path (indexing new content into BM25 during ingestion). This is the path that future document ingestion will use. A complete verification would have indexed a test chunk and confirmed it appeared in BM25 results. The test was deliberately minimal per the plan, but it leaves the incremental indexing path unverified until real use.

## Lessons Learned

- BM25 integrates cleanly into asyncio via run_in_executor — same pattern as FAISS
- rank_bm25 doesn't support incremental update; rebuild from corpus each time (fast at 12k docs: ~1s)
- pythainlp newmm tokenizer works directly for BM25 corpus tokenization — no extra preprocessing needed
- Always prefer non-mutating dict access when extracting fields from loaded data
