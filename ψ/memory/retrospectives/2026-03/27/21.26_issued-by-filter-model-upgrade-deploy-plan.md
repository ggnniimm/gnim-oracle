## Honest Feedback

**1. Model upgrade should have been proactive.** `gemini-2.0-flash` deprecation has been announced for a while. I had it in config and never flagged it as a risk. When the error appeared, I guessed `gemini-2.5-flash-preview-04-17` from memory without verifying — and wasted a rebuild cycle. Should have run `client.models.list()` first before guessing.

**2. `max_output_tokens` should have been higher from the start.** 4096 is too low for a system that retrieves 30 chunks and generates detailed legal answers. This should have been caught in eval — if any eval answer was truncated, it would have shown up as a mustcontain failure. Worth checking if any past eval failures were actually truncation artifacts.

**3. Deploy plan is thorough but doesn't account for re-index time on server.** The plan says "~40 min" but that was on Mac. On KVM2 running Docker + making Gemini embedding API calls, it could be 60-90 minutes. Should have flagged this more clearly so Ming doesn't expect a quick deploy day.

## Lessons Learned

1. **Always ListModels before guessing model name** — Gemini model IDs change with deprecations. Don't guess from memory; call the API and confirm the exact name before setting in config.
2. **`max_output_tokens` should match expected output length** — For RAG systems with 30+ chunks and detailed Thai legal answers, 4096 is too tight. Set 8192+ from the start.
