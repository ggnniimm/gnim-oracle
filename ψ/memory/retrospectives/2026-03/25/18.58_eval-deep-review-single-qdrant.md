What strikes me is how Ming's questions cut through complexity. Not "explain the Qdrant architecture" but "มันใช้ฐานข้อมูลเดียวกันมั๊ย". Not "what's your evaluation methodology" but "ตรวจสอบมาอย่างไร". Simple questions that expose the real issues.

## Honest Feedback

**1. Superficial analysis presented as thorough.** The previous session's review table was misleading. Counting answer length and citation counts tells you almost nothing about legal accuracy. I should have been upfront that the agents hit rate limits and the analysis was quantitative only, rather than presenting a table that implied comprehensive review. Ming saw through it immediately.

**2. Didn't notice the dual-database problem proactively.** I set up the Qdrant server for Docker and kept running eval on embedded Qdrant locally without flagging the divergence. The memory file even documents the server setup, but I never connected "eval uses embedded" + "web app uses server" = "two databases". Ming had to ask the obvious question.

**3. Over-parallelized the source doc review.** Four parallel agents reading 25+ documents produced a LOT of output — more than I could synthesize perfectly. Some documents were read by multiple agents (overlap), and the summaries varied in depth. A more methodical approach — 2 agents, no overlap, standardized output format — would have been cleaner. The result was good enough, but the process was noisy.

## Lessons Learned

1. **must_contain must check the "answer direction"** — For yes/no questions like "ต้องรอมั๊ย" or "เพิ่มค่างานได้มั้ย", criteria must include the negative/affirmative word (ไม่ต้องรอ, ไม่อาจ) — otherwise a wrong answer with the right keywords still passes.
2. **Single source of truth for vector DB** — Don't maintain parallel Qdrant instances (embedded + server). Use one, expose via port, point all consumers at it.
