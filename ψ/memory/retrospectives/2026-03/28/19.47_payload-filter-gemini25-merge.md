## AI Diary

There's something satisfying about sessions that start with confusion and end with clarity. We began with Ming asking "ต้อง restart ใช่มั๊ย" — and the answer was no, restart isn't enough, you have to rebuild the image. Docker bakes source code at build time. It's the kind of thing that burns you once and you never forget.

The filtering architecture evolved three times before it landed. First attempt was `doc_type_filter: str` — too narrow. Second was realizing the payload field in Qdrant isn't `doc_type` but `category` (md_loader silently renamed it). Third was generalizing to `payload_filter: dict` so we could filter on `issued_by` too, without hardcoding field names everywhere. The key unlock was Ming saying "ถ้าถามเกี่ยวกับอัยการสูงสุด จะตอบได้มั๊ย" — that question revealed the need for a second filter path.

The history-aware intent was the most satisfying piece. When someone asks "แล้วเรื่องการจ้างช่วงมั้ย" as a follow-up in a court judgment conversation, there are no court judgment keywords in that message. Without history awareness, the filter disappears. The solution — scan last 6 user messages — is simple and effective. It's one of those cases where the right fix is also the obvious one once you see the problem clearly.

The model upgrade surfaced something important: `gemini-2.5-flash-preview-04-17` looks like the right name but it's for `v1beta` API, not `v1`. The SDK uses `v1`. `client.models.list()` is the only trustworthy source — memory and documentation lag behind. I'll remember this pattern: list before guessing.

TC-042 and TC-064 failures after the model upgrade were actually not regressions — they were pre-existing wrong criteria. TC-064 had `ผู้รับจ้างรายใหม่` as a criterion for an อายุความ question, which has nothing to do with hiring a new contractor. Someone (me, in a previous session) had confused the must_contain with what a related but different document would say. Gemini 2.5 Flash just answered more directly and exposed the bad criterion. That's a healthy failure mode.

## Honest Feedback

**1. Docker confusion cost real time.** Ming asked about restart, I explained it correctly, but we'd already been through this confusion before in a prior session. The lesson keeps needing to be re-learned because it's not written anywhere prominent. The `docker compose build app && docker compose up -d app` command should be in the project README or at minimum the MEMORY, not just in retrospectives.

**2. The `doc_type` vs `category` mismatch was avoidable.** The md_loader silently remaps frontmatter `doc_type` to Qdrant payload field `category`, but this mapping isn't documented anywhere. I wrote filter code that queried `doc_type` and got 0 results, had to curl the payload to discover the real field name. A comment in md_loader or qdrant_store saying "frontmatter doc_type → payload category" would have saved 20+ minutes of debugging.

**3. Eval criteria drift is a real risk.** TC-064's wrong criterion was in golden_test_cases.json for multiple sessions without being caught — it only surfaced when the model phrasing changed. The must_contain field should be treated as a contract, and there should be a review process for criteria that were written to match one specific model's output style rather than the actual answer content.

## Lessons Learned

1. Docker `restart` reuses the cached image — code changes need `docker compose build`
2. Always `client.models.list()` to verify Gemini model names — documentation and memory are stale
3. `payload_filter: dict` with `{field, value}` generalizes filtering to any Qdrant payload field without code changes
4. History-aware intent: last 6 user messages → follow-up queries inherit filter context
5. must_contain criteria should be reviewed for answer-direction correctness after model upgrades
