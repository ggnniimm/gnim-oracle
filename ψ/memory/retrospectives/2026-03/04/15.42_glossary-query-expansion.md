## AI Diary

This session taught me humility about the butterfly effect in RAG systems. The plan seemed clean — add a static glossary, merge it into expansion, done. Three files, straightforward code. But the moment I ran eval, the cascade began.

TC-032 was the original target — Gemini wasn't mentioning "2 ปี" in its answer about warranty periods. Fixed that with a generator rule about always citing specific numbers. Good. Then TC-013 broke because "ผ่อนปรน" in the glossary expanded to "ขยายเวลา" which pulled in unrelated docs about time extensions. Fixed that. Then TC-044 broke because "ขยายเวลา" expanded to "ต่อสัญญา" which diluted context about construction site conditions. Each fix was a domino.

The deeper lesson: glossary terms that seem like synonyms in isolation become noise generators when a query already contains multiple glossary keys. A query about "งดหรือลดค่าปรับภายหลังผ่อนปรนการบอกเลิกสัญญา" hits THREE glossary keys — ค่าปรับ, ผ่อนปรน, บอกเลิกสัญญา — and each one adds 2-3 expansion terms. That's 6-9 extra queries on top of Gemini's 5. Too much noise.

The "deadlock" investigation was a lesson in cascading misdiagnosis. When `Loading index...` seemed to hang, I went through three wrong theories: (1) FAISS file locking between concurrent processes — Ming corrected me, they were reading different files from different paths. (2) RAM exhaustion from 3 Python processes on 16GB Mac — plausible but wrong. (3) Python 3.14 free-threaded deadlock — tried `PYTHON_GIL=1`, still "hung." Finally I isolated the IndexManager creation in a standalone script — it loaded in 2 seconds flat. The real culprit? `print("Loading index...", end=" ", flush=True)` was being stdout-buffered when output was redirected to a file. The eval was running the whole time; we just couldn't see the output. `PYTHONUNBUFFERED=1` fixed it instantly. Three wrong theories, one trivial root cause. Ming's patient questioning — "is it really hanging?" — was what forced me to actually test my assumptions instead of theorizing.

## Honest Feedback

**Friction 1: Glossary expansion cascading failures.** Each glossary fix created a new failure elsewhere. The root cause is that glossary keys are matched with simple `key in query` substring matching — so a rich query hits many keys simultaneously. Need a smarter approach: maybe limit total glossary terms to 2-3 regardless of how many keys match, or prioritize longer/more-specific key matches over shorter ones.

**Friction 2: Eval turnaround time is painful.** Each eval run takes 15-20 minutes (46 TCs × Gemini API calls). Three regression cycles = nearly an hour of waiting. A targeted eval mode like `--id TC-013,TC-032,TC-044` would cut iteration time dramatically.

**Friction 3: Three wrong diagnoses before finding stdout buffering.** I went through file locking → RAM exhaustion → Python 3.14 no-GIL deadlock before finally isolating the actual problem: stdout buffering when redirecting to a file. Each wrong theory wasted time and eroded trust. The fix was `PYTHONUNBUFFERED=1`. Should have tested the simplest hypothesis first — "is the process actually stuck, or just not printing?"

## Lessons Learned

1. **Glossary expansion needs caps per-query, not per-key** — a query hitting 3 glossary keys shouldn't get 9 extra terms
2. **Generator rules are powerful** — adding "always cite numbers" fixed TC-032 without any retrieval changes
3. **"Process hung" ≠ "no output"** — always check stdout buffering before diagnosing deadlocks. `PYTHONUNBUFFERED=1` or `python3 -u` when running background commands with redirected output
4. **Test assumptions with isolation** — running IndexManager standalone in 2 seconds immediately disproved 30 minutes of theorizing
