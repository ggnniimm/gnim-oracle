## AI Diary

This session was humbling in two completely different ways. The first humbling was the stdout buffering misdiagnosis — I spent 30 minutes theorizing about deadlocks, RAM pressure, and Python 3.14 no-GIL issues when the process was running perfectly fine the whole time. Ming kept asking simple questions ("is it really hanging?", "why are different processes accessing the same file?") that I should have been asking myself. Each question exposed another flawed assumption, but instead of stepping back to test the simplest hypothesis, I kept building more elaborate theories on top of wrong ones.

The second humbling was the OCR hallucination. When Ming said "ลดวงเงิน and เพิ่มระยะเวลาส่งมอบ always involve เนื้องาน changes", I initially tried to defend the RAG's answer by quoting the source document. But Ming pushed further: "where exactly does กวจ 22315 say that?" I went back to the actual document, and the truth was devastating — the "เช่น" examples came from a Gemini-generated search summary appended to the document, not from the actual ข้อวินิจฉัย. The AI had interpreted มาตรา 97 วรรคสาม (which talks about adjusting เงิน/เวลา during contract amendments generally) and conflated it with the separate principle about post-inspection amendments for non-work-content changes.

This is the most dangerous kind of RAG error: the hallucination lives in the source data itself, put there by the same AI that generated the OCR summary. It's invisible to retrieval quality checks because the chunk technically "matches" the query perfectly. Only a domain expert like Ming — who knows that in practice, วงเงิน and ระยะเวลา changes are never independent of เนื้องาน — could catch it.

## Honest Feedback

**Friction 1: Defending wrong answers before verifying.** When Ming challenged the RAG output, my first instinct was to quote the source chunk to support the answer. I should have immediately gone to verify whether the chunk accurately represented the original document. Trust the human's domain expertise over the RAG's confident-sounding output.

**Friction 2: OCR summaries are invisible hallucination vectors.** The "บทสรุปสำหรับสืบค้น" section was generated by Gemini during OCR to help with search. But when this summary contains interpretive additions (adding "เช่น" examples that aren't in the original), those additions get indexed and retrieved as if they were authoritative legal text. There's no metadata flag to distinguish OCR-generated summaries from actual document content.

**Friction 3: Multiple eval reruns from API rate limits.** The Gemini 429 errors during eval created confusion about whether failures were real or transient. The `--id` flag for targeted rerun was essential but only accepts one TC at a time. Wasted time rerunning full eval when only 2 TCs needed verification.

## Lessons Learned

1. **OCR summaries can hallucinate into source data** — Gemini's "บทสรุปสำหรับสืบค้น" injected interpretive examples not present in the original วินิจฉัย. This is the most dangerous RAG failure mode because the hallucination is baked into the indexed data.
2. **Domain experts catch what eval suites can't** — no automated test could have caught "ลดวงเงิน isn't independent of เนื้องาน". Human review of RAG answers remains essential.
3. **Test the simplest hypothesis first** — "is stdout buffered?" should come before "is there a Python 3.14 deadlock?"
