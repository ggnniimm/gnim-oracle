## Honest Feedback

**Friction 1: Qdrant local lock contention.** The background eval task from the first attempt held the Qdrant lock, blocking the second attempt. Local Qdrant (SQLite-backed) doesn't support concurrent reads. This has bitten us before. The warning at startup ("not recommended for >20K points") is also concerning. We should consider migrating to Qdrant in Docker for the 28,897-point collection — it would eliminate lock issues and improve performance.

**Friction 2: Eval takes ~22 minutes.** 66 TCs * ~20s each = 22 min minimum. This is slow enough that I have to run it in background and wait. For a verification-only session, the eval is most of the wall-clock time. A subset/smoke-test mode that runs only the historically flaky TCs (029, 031, 035, 045, 051) would give faster feedback during development.

**Friction 3: Branch scope creep.** `feat/admin-court-judgments` has grown well beyond court judgments. It now includes infra (Dockerfile, parallel eval), retrieval (law-chunk fallback, category boost), and generation (prompt rules) changes. This makes the eventual PR harder to review. Future work should use smaller, more focused branches. But for a solo project with rapid iteration, the broad branch served its purpose.

## Lessons Learned

1. **Verification sessions are valuable** — a short session dedicated to "commit and verify" catches issues (like the Qdrant lock) before they compound
2. **66/66 is achievable but not guaranteed** — LLM variance means the score floats between 64-66. The system works; the generation model is the remaining variable.
