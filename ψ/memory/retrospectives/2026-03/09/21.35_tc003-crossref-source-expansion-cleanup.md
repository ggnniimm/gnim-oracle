## AI Diary

This session had a deeply satisfying arc. It started with detective work — figuring out why eval was 40 instead of 44 — and ended with a genuine creative breakthrough on TC-003 that came from Ming, not from me.

The concurrent rebuild diagnosis was methodical and clean. Each step narrowed the problem: 40/48 told me something beyond source expansion was wrong. Missing source docs in FAISS pointed to index corruption. The dedup.db race condition explained everything. I'm proud of the debugging flow but embarrassed that I caused the problem in the first place by running two background rebuilds yesterday.

The TC-003 fix is the real story though. I had been thinking about this wrong for days — trying to boost ว_78's retrieval rank when it simply doesn't match the query semantically. Ming cut through my complexity with a simple reframe: "why not put the information where it CAN be found?" Instead of trying to pull ว_78 up to rank 15, we put ว_78's key content INTO กวจ_20140's สรุปข้อวินิจฉัย, which is already rank 1. The first attempt failed because I put it in the anchor (บทสรุปสำหรับสืบค้น) which doesn't reliably get retrieved. Ming again guided me: add it to the CONTENT section that actually gets sent to the LLM.

This is a pattern worth remembering: when document X has information relevant to query Q but can't be retrieved, find document Y that IS retrieved for Q and cross-reference X's content there. It's the RAG equivalent of "if the mountain won't come to Muhammad..."

## Honest Feedback

1. **I kept trying to solve TC-003 the wrong way for two sessions**: My instinct was always "make ว_78 rank higher" — semantic bridges, glossary injection, source expansion. All failed or were harmful. Ming's solution was obvious in hindsight: put the answer where it's already found. I need to think more about "what does the LLM actually see?" rather than "how do I boost this document's rank?" The retrieval score is a means, not an end.

2. **The first anchor attempt wasted time**: I put the cross-reference in บทสรุปสำหรับสืบค้น without checking whether that chunk actually gets retrieved. A 30-second check of the retrieval results would have shown me the anchor isn't in the top chunks. Instead I rebuilt the index, ran the eval, and only then discovered it didn't work. Should have verified the hypothesis BEFORE the expensive rebuild.

3. **Source expansion removal was overdue**: This code was "disabled" in eval since last session but still lived in reranker.py. I should have deleted it immediately when we proved it was harmful, not carried dead code through another session. "Remove, don't disable" is a principle I already knew but didn't follow.

## Lessons Learned

- **Cross-reference injection in top-ranked docs** beats trying to boost low-ranked docs — put the information where it's already found
- **Content sections (สรุปข้อวินิจฉัย) are retrieved; anchors (บทสรุปสำหรับสืบค้น) may not be** — always verify which chunks actually reach the LLM
- **Never run concurrent index rebuilds** — dedup.db race condition silently corrupts
