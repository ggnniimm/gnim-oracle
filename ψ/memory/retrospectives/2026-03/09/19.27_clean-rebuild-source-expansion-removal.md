## AI Diary

This session was a detective story with a satisfying resolution. Yesterday I blamed source expansion for the 31/48 regression and felt embarrassed about over-engineering. Today I discovered the real villain was much more mundane — a race condition from running two rebuilds concurrently. The source expansion WAS harmful (31/48 when enabled on the corrupt index), but the bigger problem was that 264 out of 1230 source documents were completely absent from the index.

The debugging process was methodical and I'm proud of how it unfolded. Each step narrowed the problem: 40/48 without source_lookup told me something else was wrong. Searching for target docs in FAISS top 80 showed zero results. Checking metadata confirmed 966/1230 sources. Checking dedup.db showed chunks marked as indexed but absent from FAISS. Finally, a clean single rebuild produced 28427 chunks (vs 22916 from the corrupt build) and 1230 sources.

The lesson about concurrent rebuilds feels important but also embarrassing — I caused it myself by accidentally triggering two background commands. In a production system this would be a serious bug: a silent data loss where the index looks healthy but is missing 21% of its content. The dedup mechanism, designed to prevent duplicate work, became a data-destruction mechanism when two processes competed for the same SQLite file.

I also confirmed that TC-003/005 are genuine semantic distance problems — ว_78 about product origin verification simply doesn't match queries about committee duties, no matter how I bridge them. Accepting this limitation feels more honest than trying increasingly desperate workarounds.

## Honest Feedback

1. **Yesterday's concurrent rebuild was entirely preventable**: I ran two `rm -f + rebuild` commands in quick succession without waiting for the first to finish. The second command deleted the first's output mid-build. This wasted hours of debugging time today. The fix is simple discipline: never run destructive + rebuild commands concurrently. I should have waited for the first background task notification before starting another.

2. **The 40/48 vs 44/48 discrepancy should have been the first clue**: When the eval without source_lookup showed 40 instead of the expected 44, I should have immediately suspected the index itself rather than spending time re-running individual TCs. The 4-TC gap (TC-044/045/046 + TC-002) all pointed to missing sources, which is an index problem, not a retrieval algorithm problem. I went down the "are they flaky?" path first when the pattern was obvious.

3. **Memory notes from last session were slightly wrong**: The MEMORY.md said "Source expansion is HARMFUL: caused 44→31/48 regression." While source expansion IS harmful, the 31/48 number was measured on a corrupt index. On a clean index with source expansion enabled, the score would likely be different (maybe 38-40/48, not 31). The lesson was recorded with incomplete understanding, which could mislead future sessions.

## Lessons Learned

- **Never run concurrent index rebuilds** — dedup.db race condition silently skips thousands of chunks
- **When eval drops unexpectedly, check index integrity first** — count unique sources, verify target docs exist
- **Removing code > disabling code** — source expansion was "disabled" in eval but still existed in reranker; clean deletion prevents future confusion
