## AI Diary

This session was a masterclass in the unglamorous reality of RAG systems — data hygiene. The exciting work was done in earlier sessions (Qdrant migration, law-aware chunking, embedding model upgrade). This session was about cleaning up the mess those changes left behind.

Ming's frustration was entirely justified. Having two data directories with different index states is confusing, and I should have caught this divergence earlier. The root cause is simple: `data_with_ac/` was created as a safe sandbox for experimenting with court judgment data, but then infrastructure changes happened on `data/` — and nobody synchronized them. It's the classic branching problem applied to data instead of code.

The eval drill-down methodology worked well. Running each failing TC 2-3 times to distinguish consistent failures from LLM variance is now a proven pattern. Out of 6 failures, 4 turned out to be random variance — the LLM sometimes includes `มาตรา 103` and sometimes doesn't. Only TC-011 and TC-051 are real retrieval gaps where the relevant source document consistently isn't in the top results.

The decision to use cross-references (option 2) for fixing TC-011 and TC-051 is the right call. It's the same pattern that worked for TC-001 and other consistent failures: inject the missing information into a document that IS consistently retrieved. Track it in GitHub issues so it doesn't get lost.

What surprised me was that adding 151 court judgment files (1,152 new chunks) actually improved eval from 58/66 to 60/66 rather than causing regressions. More data in the vector store means more competition for retrieval slots, which usually hurts. But court judgments are sufficiently different from ข้อหารือ that they don't interfere — they serve different queries.

## Honest Feedback

1. **Two-directory confusion was avoidable**: The `data_with_ac/` experiment should have been merged back or clearly documented much earlier. When infra changes happened on `data/`, the divergence became invisible. A simple `CURRENT_DATA.md` marker file in each directory would have prevented the confusion.

2. **No automated regression detection**: We rely on running eval manually and eyeballing results. With 66 TCs, it takes ~7-10 minutes per run (with 3 workers). There should be a CI-like mechanism that runs eval on data changes and flags regressions automatically — even just a local git hook.

3. **LLM variance is unsolved at the root**: 4 out of 6 failures were LLM variance. The must_contain approach is brittle — it checks for exact phrases that the LLM may or may not include. A semantic similarity check ("does the answer convey the concept of มาตรา 103?") would be more robust but harder to implement.

## Lessons Learned

- Adding domain-specific data (court judgments) to a RAG system can improve eval scores rather than cause regressions, when the new data serves queries that were previously underserved
- Systematic 2-3x re-runs per TC is essential for distinguishing real retrieval failures from LLM generation variance
- Data directory divergence is as dangerous as code branch divergence — needs the same merge discipline
