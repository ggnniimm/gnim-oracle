## AI Diary

This session was a lesson in the butterfly effect of RAG systems. I went in confident — law-aware chunking was a clear improvement, the code changes were minimal, the perf fix was elegant (just skip Gemini when loading pre-processed MD). Everything worked perfectly in isolation: 0.0s parsing, beautiful `[พ.ร.บ.จัดซื้อจัดจ้างฯ 2560 | มาตรา 103]` headers, 132 sections properly parsed.

Then I ran eval and the floor dropped out. 57/66. Eight failures where there used to be one. My first instinct was denial — "it's just LLM variance." And partly it was. But the systematic 3x-per-TC analysis was humbling. TC-001 fails every single time. The mechanism is subtle: replacing 500 generic 400-char chunks with 120 section-aware chunks changes the embedding landscape. Vectors that used to be near a query in embedding space are now further away because the text boundaries shifted. A chunk that used to contain "ความสัมพันธ์" in a 400-char window now sits inside a larger section chunk where that keyword is diluted among 1500 chars of legal text.

This is the fundamental tension in RAG: bigger chunks = better context for the LLM, but worse precision for retrieval. Law-aware chunking is still the right call for queries like "มาตรา 103 วรรค 3" — but we need to verify each TC and potentially adjust cross-references or eval criteria. The honest truth is that I should have run eval *before* deleting the old chunks, so I could A/B compare.

## Honest Feedback

1. **No rollback plan**: I deleted old `.pdf` chunks from Qdrant before running eval. Should have kept them temporarily and compared retrieval results side-by-side. The migration script exists for adding data but there's no snapshot/restore mechanism for the collection. This is a systemic gap — any vector store change is one-way.

2. **Eval infrastructure is too slow for iteration**: 66 TCs × ~20s each = ~22 minutes per eval run. When debugging regressions, I need to run eval multiple times. The sequential nature of `run_eval.py` makes this painful. Ming asked "ทำไมไม่รัน eval พร้อมกัน" — and he's right. Parallel eval with Qdrant server mode should be trivial now.

3. **`--force-reindex --file` doesn't clean up old source_name variants**: The script looks for exact `source_name` match to delete old vectors, but when the source changed from `.pdf` to `.md`, it found nothing to delete. This left ghost data that I had to clean manually. The reindex tool should search for the file stem, not the exact name.

## Lessons Learned

- Law-aware chunking changes embedding landscape — bigger section chunks dilute keyword density, shifting which documents get retrieved for keyword-heavy queries
- Always run eval BEFORE deleting old data from vector store — keep both versions temporarily for A/B comparison
- `_split_paragraphs` with Gemini = 132 API calls for one law file; `use_gemini=False` makes it instant but loses semantic วรรค detection (blank-line fallback can't split PDF-formatted text without blank lines between paragraphs)
