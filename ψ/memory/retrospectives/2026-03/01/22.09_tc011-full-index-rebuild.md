## AI Diary

This session was a masterclass in debugging retrieval systems. The frustration was real — I could SEE the right chunks in the raw FAISS results, I could SEE "หัวหน้าหน่วยงานของรัฐ" at positions #5, #13, #15 in the reranked output, and yet the LLM kept answering wrong. I tried the obvious fix (more MMR extras), but it wasn't enough.

The breakthrough came when I traced the full pipeline end-to-end and realized the problem wasn't in the reranker logic — it was in the data. Stale chunks from before I edited the MD files were still sitting in the FAISS index, contradicting the correct chunks. The old 31960 summary saying "ผู้อำนวยการองค์การสะพานปลา" was confusing the LLM alongside the new chunk saying "หัวหน้าหน่วยงานของรัฐ". The index_md_folder.py only adds NEW chunks — it never removes old ones.

This is the kind of bug that's invisible unless you trace every step. The retrieval looked fine (right documents found!), the reranking looked fine (right chunks in top-15!), but the LLM was seeing ghost data from a previous life of the document. Once I rebuilt from scratch, TC-011 passed on the first try.

The 20-minute wait for re-indexing felt agonizing but was absolutely the right call. Sometimes you need to burn the index down and start fresh.

## Honest Feedback

**Friction Point 1: Append-only indexing is a time bomb.** The `index_md_folder.py` dedup system only prevents adding identical chunks — it never removes stale ones when source files change. This means every edit to an MD file creates ghost data. We got away with it during initial development because files didn't change, but now with anchor generation and manual edits, it's a real problem. Need a proper "re-index this file" command that removes old chunks first.

**Friction Point 2: Module import confusion.** I wasted 3-4 tool calls trying to import `src.retrieval.faiss_store` when it's actually `src.indexing.faiss_store`, then got the method signature wrong (`top_k` vs `k`). The codebase has retrieval and indexing modules with overlapping concerns. This cost ~5 minutes of debugging time.

**Friction Point 3: Non-deterministic LLM answers mask retrieval bugs.** TC-011 sometimes passed and sometimes failed in earlier sessions. This made it hard to know if my fixes were working or if I was just getting lucky with LLM sampling. The root cause (stale chunks) was always there, but non-determinism hid it. Need a retrieval-only eval mode that checks chunk content, not just LLM output.

## Lessons Learned

- **Stale chunks are invisible poison**: When you edit source MD files, append-only indexing creates contradictory data. The old and new chunks both exist, and the LLM gets confused by conflicting information. Full rebuild is the nuclear option but sometimes it's the only clean fix.
- **Trace the full pipeline before guessing**: Increasing MMR_INJECT_EXTRAS was a reasonable guess but wrong. Only by tracing FAISS → BM25 → dedup → MMR → source completion → LLM context did the real problem surface.
