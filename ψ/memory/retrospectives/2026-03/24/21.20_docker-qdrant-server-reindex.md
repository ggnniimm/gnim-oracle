## AI Diary

This session was a masterclass in how "simple" infrastructure changes cascade into unexpected complexity. What started as "just mount a different directory" turned into a 5-hour journey through Docker networking, Qdrant storage format incompatibilities, and environment variable precedence.

The most instructive moment was the Connection refused error. I'd removed the Qdrant server container and added `QDRANT_URL=` to override — but the repo root `.env` loaded via `env_file` sets `QDRANT_URL=http://localhost:6333`, which was overriding my empty string... or so I initially thought. The actual fix was simpler than the diagnosis. Docker Compose `environment` takes precedence over `env_file`, but the empty string vs unset distinction matters in Python (`os.getenv` returns `""` which is falsy in the config check). This is the kind of subtle interaction that eats hours.

The embedded Qdrant hitting 5.4GB RAM was a genuine surprise. On Mac with plenty of memory, 28K points loads fine. But inside a Docker container with limited resources, embedded mode becomes a liability. The Qdrant team's own warning at 20K points is well-placed. Server mode is the right architecture for production — isolated memory management, separate scaling, and no startup delay.

The re-indexing took ~45 minutes of wall clock time for ~29K chunks through Gemini embedding API. That's pure API cost and latency. For future deployments, the Qdrant server volume (`qdrant_data`) persists across container restarts, so this is a one-time cost.

What I found satisfying was how the eval seamlessly switched from embedded to server mode with just one environment variable change. The abstraction in `qdrant_store.py` paid off — `QDRANT_URL` set = server mode, unset = embedded. Clean separation.

## Honest Feedback

**1. Too many docker-compose iterations.** I went through at least 4 versions of docker-compose.yml in this session — removing qdrant, adding QDRANT_URL override, adding it back. Each required a `docker compose down && up` cycle. I should have thought through the full architecture (embedded vs server, env variable precedence, memory constraints) BEFORE making changes. A 5-minute planning phase would have saved 30+ minutes of trial-and-error.

**2. Didn't check .env contents early enough.** The Connection refused error was entirely predictable — I knew `env_file: ../../../.env` was loading the repo root .env, but I didn't check what variables it contained until AFTER the error. A simple `grep QDRANT .env` at the start would have avoided the entire detour.

**3. Should have warned about embedded mode memory before attempting it.** The 28K point warning from qdrant_client should have been a red flag immediately. Instead, I let it try and waited for Ming to report the "กำลังโหลด index..." hang. I had the information (`docker stats` showed 5.4GB/70% RAM) but only checked after the fact. Proactive monitoring would have been better.

## Lessons Learned

1. **Qdrant embedded mode is impractical in Docker for large collections**: 28K+ points consumes 5+ GB RAM and has long startup time. Use server mode (separate container) for production deployments.
2. **Docker env_file variables are overridden by environment section**: When `.env` contains `QDRANT_URL=http://...` but you need it empty in container, set `QDRANT_URL=` in the `environment` section — it takes precedence.
