TC-065 was interesting because the failure was caused by a question-type mismatch: the question asks "คืออะไร" (definitional) but the must_contain checked for "ชดใช้" (a consequence word). The LLM was doing the right thing — answering the question as asked — and the test was checking for something that only appears in "what are the consequences?" answers. The fix was OR logic to accept either the consequence word or the more natural outcome word "รับผิด".

What struck me is the pattern: every LLM variance issue we've seen in this project comes down to the same root cause — the test expects a specific surface-form word, but the LLM reasonably uses a synonym or focuses on a different but equally valid aspect of the answer. The solution is always to widen the criterion: OR logic, alternatives, or dropping the too-strict requirement entirely. We've now done this for TC-011, TC-030, TC-044, TC-051, TC-065. Five TCs stabilized by accepting variation rather than forcing uniformity.

## Honest Feedback

**Friction 1: Question-type vs. criterion mismatch is a recurring blind spot.** TC-065 was flagged as "LLM variance" but it was actually a design error — the must_contain criterion didn't match the question type. "คืออะไร" naturally yields definition, not consequence. We should have caught this when writing TC-065. Lesson: when writing must_contain, think "would a correct answer to THIS EXACT QUESTION reliably contain this word?" not "does the source doc contain this word?"

**Friction 2: Export is blocking and slow.** The tc_answers.csv export runs synchronously for 66 TCs × ~25s = ~28 min. There's no progress indicator beyond stdout. Running as background job helps, but it still blocks the terminal and requires waiting. Could benefit from a `--parallel N` flag or at minimum a progress ETA. Not critical but adds friction to iterative refinement.

**Friction 3: Two separate /rrr calls today for one logical session.** The session was continuous but I wrote two retros (17:08 and 20:51). The skill doesn't have guidance for "append to today's retro" — so each /rrr creates a new file. This is fine architecturally (vault accumulates), but reading back "what happened on 2026-03-16" requires reading two files instead of one. Minor fragmentation.

## Lessons Learned
- must_contain criteria must match the question TYPE (definitional vs. consequence vs. procedural) — not just "does the doc contain this word"
- OR logic (`["word1", "word2"]`) is the right tool when the concept is stable but the surface form varies
