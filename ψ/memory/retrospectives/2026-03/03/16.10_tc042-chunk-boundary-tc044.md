## AI Diary

This session was a masterclass in "the answer is never where you first look." I started thinking the problem was simple — chunk 22 of document 2132 has "ไม่ต้องรอผู้ทิ้งงาน" but doesn't get retrieved. Easy fix: shorten the bullets so they fit in one chunk. Except... that was only layer one.

Layer two: I'd been deleting the wrong index files for multiple rebuilds across sessions. `data/faiss_index.bin` doesn't exist — the real file is `data/faiss_index/index.faiss`. Every "clean rebuild" was actually appending to the old index, creating a 43k-vector monster with duplicate chunks. This bug had been hiding since previous sessions. Finding it felt like discovering a crack in the foundation of a house you've been decorating.

Layer three: even after a truly clean rebuild, the shortened bullets ranked worse in FAISS because arrow notation (→) doesn't match query terms as well as verbose Thai prose. The fix that was supposed to help actually hurt retrieval rank — from position 8 to position 85, outside the dedup pool entirely.

The real solution was lateral: stop trying to get 2132 into the results, and instead put the critical knowledge INTO a document that already ranks #1 (18077). Cross-referencing is the design pattern for this system — the knowledge network matters more than any single document's chunk boundaries.

Four full index rebuilds in one session (~23 min each). One crashed from a network error. That's about 90 minutes of waiting for embeddings. The patience required for this kind of work is real.

## Honest Feedback

**Friction 1: Index rebuild is the bottleneck.** 23 minutes per rebuild, and this session needed 4. That's 90+ minutes of dead time. There's no incremental update — FAISS doesn't support selective delete, and the index script's dedup is hash-based so changed text creates new entries alongside old ones. Need a "rebuild single file" workflow that actually works.

**Friction 2: Wrong index paths across sessions.** I (and previous sessions) were deleting `data/faiss_index.bin` and `data/bm25_index.pkl` — files that don't exist. The real paths are `data/faiss_index/index.faiss` and `data/bm25_index/bm25.pkl`. This should be documented or the delete-and-rebuild should be a single script command. The fact that this was wrong for multiple sessions means every "clean rebuild" before today was actually contaminated with old chunks.

**Friction 3: Dedup pool cutoff is a hidden cliff.** `RERANK_TOP_K * 5 = 75` is the maximum number of candidates for MMR. If your critical chunk is at FAISS rank 76+, it's invisible — no amount of source completion or prompt tuning will help. This parameter silently determines what knowledge can reach Gemini, and it's buried in the reranker code.

## Lessons Learned

1. **Cross-referencing trumps chunk optimization** — when a document can't rank high enough for a query, put the critical fact in a document that does
2. **Verify your file paths** — `data/faiss_index.bin` ≠ `data/faiss_index/index.faiss`; wrong paths silently succeed (rm -f doesn't error on missing files)
3. **Shortened text can rank worse** — FAISS cosine similarity rewards matching vocabulary; concise arrow notation (→) loses semantic overlap with query terms
4. **The dedup pool is a hard ceiling** — at `top_k * 5 = 75`, anything ranked lower is unreachable regardless of source completion settings
