# New helper for single-page render (avoids re-rendering whole PDF on fallback)
def _pdf_page_to_image(pdf_bytes, page_idx, dpi=300) -> bytes:
    import fitz
    doc = fitz.open(stream=pdf_bytes, filetype="pdf")
    try:
        zoom = dpi / 72
        mat = fitz.Matrix(zoom, zoom)
        pix = doc[page_idx].get_pixmap(matrix=mat, colorspace=fitz.csRGB)
        return pix.tobytes("png")
    finally:
        doc.close()

## Architecture Decisions

- **Single-page re-render** instead of re-rendering whole PDF on fallback (cheap helper, only runs on failure).
- **Try-once at 200 DPI** rather than recursive DPI reduction. Empirical data showed 200 DPI is enough; further reduction would risk OCR accuracy.
- **Keep 300 DPI as default**, not lower the baseline. 300 DPI works fine for most pages; we only pay the re-render cost on failures.
- **Did NOT change LONG_DOC_PAGE_THRESHOLD again** — 10 pages is a good safety boundary. Streaming the verbatim template is unstable for anything over that.

## Honest Feedback

Three friction points worth naming:

**1. I anchored on the wrong root cause for too long.** "Streaming 429" and
"rate exhausted" were real but secondary. The primary cause was upload payload
size. I knew the page bytes (logged them: 4MB, 3.9MB...) but didn't connect
"large bytes" → "slow upload" → "timeout in fixed window." Ming connected it
in one sentence. I should pre-mortem failure modes more rigorously: what's the
*physical* time budget vs. *what's actually happening*?

**2. The retry script and the production code diverged.** `retry_failed_pages.py`
was a separate path with its own logic. When I made the 200 DPI insight, I had
to remember to *also* port the fix into `ocr.py`. If the retry script had been
a thin wrapper around the production extraction code, the fix would have
propagated for free. Tech debt: two parallel extraction code paths.

**3. TaskOutput truncation broke my progress visibility.** I had to fall back
to `tail -120 /tmp/retry_lowdpi.log` to see what was happening. The notifications
on completion are nice but the in-flight observability is limited. Could have
saved attention budget by checking the log file directly from minute 5.

## Lessons Learned

1. **For image-API calls, payload size is often the bottleneck, not rate limits.** Before assuming "rate-limited," check upload time. A 4MB PNG over a non-ideal route can eat the entire per-call timeout window.

2. **Don't lower the default; add a fallback.** Keeping 300 DPI as primary preserves quality on the happy path; falling back to 200 DPI only on failure keeps the cost where it belongs.

3. **Test the alternative hypothesis even when the primary fits.** "It's rate limits" fit the 429s. "It's upload size" *also* fit them and additionally explained the pure timeouts. The second hypothesis was the real one.

4. **Workaround → durable fix in same session.** The temptation after a long retry success is to declare victory and move on. Wiring the insight into production code while the context is fresh is high-leverage.
