**1. ฉันเขียน script แบบ "happy path" คิดไม่ถึงเคสที่ไม่สมมาตร** — sync_md.sh แรกๆ ออกแบบจากสมมุติฐานว่า local กับ prod "ควรจะ" เหมือนกัน ไม่ได้คิดว่าระหว่างการ migrate อาจมี orphans ที่ฝั่งใดฝั่งหนึ่ง destructive default (`--delete`) คือ tech debt ที่ติดมาตั้งแต่นาทีแรก ครั้งหน้าก่อนเขียน sync/cleanup script ให้ ask "ถ้าฝั่ง src ไม่มีอะไรเลย dst ควรว่างไหม?" ก่อนใส่ `--delete`

**2. การ pattern-match กับเคสล่าสุดยังเป็น weakness ที่ตอบโต้ไม่ทัน** — แม้มี feedback memory เตือนแล้ว ฉันก็ยังเผลอ การที่เพิ่งแก้ dedup bug ของ ว189 มา 5 นาทีก่อน ทำให้สมองหยิบสมมติฐานเดียวกันมาใช้ทันที โดยไม่ตั้งคำถามว่า "เคสนี้อาจไม่ใช่ปัญหาเดียวกัน" — ต้องการ external nudge ("งงรึป่าว") เพื่อจะหยุดคิด

## Lessons Learned

### check-filter-before-debug-empty (saved to memory)
เห็น 0 chunks/empty result จาก indexer → grep status/quality ก่อน อย่ากระโดดไป fix dedup/code

### Destructive defaults are tech debt
`rsync --delete`, `git push --force`, `rm -rf` — ทุกครั้งที่ตัวเลือก "ตัด state ของอีกฝั่งทิ้ง" เป็น default แทนที่จะเป็น opt-in คือ tech debt ที่ติดตัว script ตั้งแต่นาทีแรก เปลี่ยนเป็น opt-in เสมอ ใส่ warning เมื่อเปิด

### Pull-first as backup pattern
ก่อน prune ใดๆ ระหว่าง local กับ prod ให้ pull ครบก่อน — local กลายเป็น backup snapshot ที่ตัดสินใจครั้งหน้าได้โดยไม่ต้องกลัวข้อมูลหาย
