## Honest Feedback

**3 friction points:**

1. **Retry strategy ผิดระดับ**: `ocr_with_retry` retry ทั้งไฟล์เมื่อ anchor fail แต่ควร retry เฉพาะ anchor (non-fatal) หรือเฉพาะ structure call ไม่ใช่ทั้ง classify + extract + structure อีกรอบ การ retry ทั้งก้อนทำให้เสียเวลา 70+ นาทีโดยไม่จำเป็น

2. **Streaming 429 diagnose ยาก**: 200 OK misleading มาก ถ้าไม่ดู timestamp อย่างละเอียด (80s gap) จะไม่รู้ว่า fail mid-stream ไม่ใช่ fail ที่ start ต้องนับ "200 OK → X วินาที → attempt N failed" ถึงจะเข้าใจว่ามัน stream fail

3. **ต้อง kill+fix+restart หลายรอบ**: session นี้ kill process 3 ครั้ง แต่ละครั้งสูญ progress บางส่วน ถ้า fix code อยู่ใน running process ได้ (hot reload) หรือถ้า structure call มี retry logic ข้างใน (ไม่ depend on outer retry) จะดีกว่ามาก

## Lessons Learned

1. **Raw cache ต้องอ่านได้ ไม่แค่เขียน**: checkpoint pattern ต้องมี resume logic ด้วย — ถ้า write-only มันเป็นแค่ waste disk I/O
2. **200 OK ≠ success ใน streaming API**: ต้อง handle mid-stream error แยกจาก connection error
3. **Retry granularity matters**: retry ทั้งไฟล์เมื่อ anchor fail เป็น over-retry — ควร fail fast และ retry เฉพาะ stage ที่ fail
