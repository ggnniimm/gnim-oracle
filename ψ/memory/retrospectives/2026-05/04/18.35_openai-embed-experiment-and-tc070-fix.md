## AI Diary

Today I learned something important about the difference between "model swap" and "model migration." When Ming asked me to find a higher-quota embedding alternative, I treated it as a technical problem with a technical solution — find a model with more RPM, switch the code, run the eval, done. I was wrong.

The 11 failures with OpenAI (70/81 vs prod 84/84) weren't a retrieval quality problem in the abstract sense. They were a *tuning debt* problem. We've spent months of iterative work calibrating cross-references, guide documents, chunk promotions, anchor injections — all designed to influence what Gemini-embedded vectors retrieve for specific Thai legal queries. That tuning is baked into the corpus structure itself. OpenAI's `text-embedding-3-large` is an excellent model, but it ranks documents by different geometric relationships. TC-063 was the clearest example: OpenAI retrieved completely different documents than Gemini for the same query. The answer was technically present in the corpus — just not at the top of the pile.

This is a non-obvious architectural truth: in a RAG system, the embedding model is not a pluggable component. It's the lens through which all retrieval tuning was done. Changing the lens invalidates every optical correction.

The quota problem remains real. ~3 RPM makes full re-index a 6+ hour ordeal and makes the system fragile during document updates. But the solution has to preserve the embedding space, not abandon it. Options: (1) request Vertex AI quota increase for the project, (2) accept slow re-index as a cost of consistency, (3) build a smart dedup-aware incremental pipeline that only re-embeds changed chunks. Option 1 is the right first move — request the quota increase now before spending more engineering time on workarounds.

One small win I'm proud of: the OpenAI batch API path is genuinely useful code even if we don't use it for production. If we ever migrate embedding providers with intent (not desperation), this code will be ready.

## Honest Feedback

**Friction 1 — Quota diagnosis took too long.** I kept trying model alternatives (text-multilingual-embedding-002, gemini-embedding-001, text-embedding-005) before establishing the key fact: Vertex AI quota is project-level, not model-level. A single `gcloud alpha services quota list` or GCP console check would have ended that exploration in 5 minutes. I went bottom-up (try each model) instead of top-down (understand quota architecture first). This is a recurring pattern — I jump to implementation before establishing constraints.

**Friction 2 — The `--no-lightrag` documentation ghost.** The plan file I wrote included `--no-lightrag` as part of the index command. Ming caught this in a screenshot ("ทำไมยังมี --no-lightrag อีก"). The flag was removed from the codebase months ago, but I had it in documentation from memory. **Friction 3 — Treating embedding model swap as a 1-hour task.** The full experiment took 9 hours: code changes, isolated infra setup, indexing, eval, analysis. The estimate for "how long will this take" was consistently optimistic. Partly because I was solving sub-problems sequentially (quota issue → code change → new quota issue → pivot to OpenAI → batch API fix → isolated Qdrant setup → eval → analysis). Each step revealed a new constraint. The root issue is that I didn't have a clear model of the total problem space before committing to the experiment. Should have sketched the risk surface (quota, infra, eval compatibility) before starting.

## Lessons Learned

1. **Embedding model ≠ pluggable component in a tuned RAG**: Cross-refs, chunk promotions, guide docs are all tuned to one geometric space. Swapping the embedding model invalidates all retrieval tuning. Treat it as a full migration, not a configuration change.
2. **Vertex AI quota is project-level**: All `aiplatform.googleapis.com/online_prediction` requests share the same pool — model switching doesn't help. Must request quota increase or switch billing accounts.
3. **Always grep flag existence before documenting**: `rg "no-lightrag" pipeline/` before writing any command with that flag.
