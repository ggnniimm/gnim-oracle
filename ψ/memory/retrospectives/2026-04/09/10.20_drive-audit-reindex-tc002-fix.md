## AI Diary

This was a satisfying session of closing loops. The previous session did the detective work — finding 40 broken Drive links, matching filenames across 6 folders, updating frontmatter. But that was only half the job. The Qdrant index still had chunks pointing to old file_ids, and BM25 was out of sync entirely.

The most interesting challenge was the dedup table. I initially tried deleting by filename, but dedup keys are Drive file_ids, not filenames. A small assumption that cost 10 minutes of "why is delete count zero?" before I inspected the actual schema. The `\x10` control character in one Thai filename was a minor surprise — invisible in most displays, only caught by repr().

The Gemini 503 storm during the first eval was frustrating but not surprising — we'd seen it before in the file_id audit session. The right response was patience: wait a day, re-run. The second run was much cleaner, and the re-run-failures-only approach quickly separated real issues from API noise.

TC-002 was the most intellectually interesting fix. The query "ครบกำหนดตรงกับวันหยุด" retrieves a doc about "ขยายระยะเวลากรณีวันหยุด" — semantically similar but legally opposite. One says "วันหยุดไม่ใช่เหตุขยาย" (can't extend for holidays), the other says "ส่งมอบวันทำการถัดไปได้" (can deliver next business day). The cross-ref technique bridges this gap: when retrieval finds the wrong angle, the cross-ref redirects the LLM to the right principle.

The must_contain issue was a reminder that keyword-based eval has a wording ceiling. "ไม่ถือว่าผิดนัด" and "ไม่ถือว่าล่าช้า" mean the same thing legally, but keyword matching doesn't know that.

## Honest Feedback

**Friction 1: BM25 has no incremental delete.** BM25Store.add_batch() appends, but there's no delete by source_name. When we deleted 2,110 Qdrant points, BM25 still had the old entries. The only fix was a full rebuild from Qdrant (56K points scrolled, pickled). For 37 files this took ~30 seconds, but it's O(n) on the entire index. A delete_by_source() method would make patching much cheaper.

**Friction 2: Dedup schema is opaque.** The table uses `source_id` as key, but what `source_id` maps to (Drive file_id? filename? hash?) isn't documented anywhere. I had to read the actual DB to discover it's the Drive file_id. A comment in the schema or a COLUMNS.md would save future debugging.

**Friction 3: Eval retry is manual.** When 56/78 TCs fail due to Gemini 503, the only option is re-run the entire suite. A `--retry-failed` flag that reads the last results file and only re-runs failures would save significant time and API quota. The manual `--id TC-XXX` loop works but is tedious for 12+ failures.

## Lessons Learned

- Dedup keys are Drive file_ids, not filenames — always inspect the actual DB schema before writing delete queries
- BM25 has no incremental delete; full rebuild from Qdrant is the only way to remove stale entries
- Cross-ref injection works even when the rank #1 doc covers the opposite angle of the same topic
- must_contain keyword eval hits a wording ceiling — semantically identical phrases need OR alternatives
