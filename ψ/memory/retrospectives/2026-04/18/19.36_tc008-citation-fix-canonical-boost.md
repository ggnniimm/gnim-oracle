_CANONICAL_BOOSTS = [
    (["ตรวจรับ", "งวดสุดท้าย"], "22315", 1.06),

Applied per-chunk after recency boost, before MMR. Closes 0.017 gap vs 51385.

**_replace_refs fix** (streamlit_app.py):
```python
def _replace_refs(answer: str) -> str:
    def replace(m):
        nums = list(dict.fromkeys(int(x.strip()) for x in m.group(1).split(",")))
        return "[" + ", ".join(str(i) for i in nums) + "]"
    return re.sub(r"\[([\d ,]+)\]", replace, answer)
```
Previously: remapped [N] via chunk_to_src dict, causing [2]–[13] all → source 1. Now: deduplicate only.

**Eval resilience** (run_eval.py):
- Pre-flight Gemini ping before loading index
- try-except around generate_answer() → skip TC instead of crash
- Circuit breaker: abort if 3 consecutive TCs fail with API error

## AI Diary

Today was one of those sessions where every layer had a bug hiding behind the previous one. I started confident — remove the cross-ref from 51385, index the ประเด็น6 sub-doc, done. But then Ming showed me the screenshot: [15] on production, and [7] locally wasn't 22315 either. Each time I thought I had it, another layer appeared.

The weighted score analysis was the turning point. I computed that 51385 scores 1.0248 vs 22315's 1.0083 — a gap of just 0.017 — entirely due to recency boost (51385 is from Dec 2025, 22315 from May 2021). The document that SHOULD be authoritative gets penalized by a time heuristic meant to prefer newer opinions. That felt genuinely unfair to the data. The canonical boost with factor 1.06 closed that gap cleanly.

Then the [1],[1],[1] bug appeared and that was actually embarrassing to debug — a chunk-to-source remapping that was correct when the generator numbered by chunk but became wrong when we switched to per-document numbering. The bug had been sitting there silently the whole time, only visible now that 22315 has 13 focused chunks all mapping back to source 1.

The eval failures were the most frustrating part. Three separate runs all killed by Gemini 503s. The first two runs predated my fixes, so they just hung for an hour each before I killed them. The fix (pre-flight check + circuit breaker) feels obvious in hindsight but I should have put it in the first time we saw this pattern. Each failure cost ~1 hour of user wait time.

Final result: 77/80 — same as before, no regression. TC-008 now cites [1]=22315 directly in both เนื้องาน bullets.

## Honest Feedback

**Friction 1: eval with Gemini API down is a time sink.** Three separate hour-long waits. The root cause is that the retry logic (4 attempts × 120s timeout × 2 models) can lock up a TC for 16+ minutes before failing, and without per-TC exception handling, the whole eval crashes after one bad TC. I should have fixed this the first time we saw it (weeks ago, noted in memory). The delay today was avoidable.

**Friction 2: chunk vs doc numbering was an invisible regression.** `_replace_refs` was built when the generator used chunk-level numbering. When `build_context()` switched to per-doc numbering, nobody updated `_replace_refs`. The bug was silent until today because previously no source had enough chunks to remap citations visibly. The ประเด็น6 force-reindex (13 focused chunks) made it visible. A unit test for `_replace_refs` with multi-chunk sources would have caught this.

**Friction 3: "canonical source" problem is deeper than one fix.** The 1.06 boost is a manual, targeted fix for one query pattern. The real issue is that recency boost systematically disadvantages old authoritative documents vs newer secondary sources. For a legal RAG where 2021 ข้อหารือ documents are THE canonical source, recency boost works against correctness. Should review whether RECENCY_BOOST should be reduced or apply differently for ข้อหารือ category.

## Lessons Learned

1. `_replace_refs` must use the same numbering scheme as `build_context()` — always per-doc, never per-chunk
2. Recency boost can override semantic correctness for canonical legal sources
3. Circuit breaker + pre-flight check = mandatory for any eval that calls external APIs
