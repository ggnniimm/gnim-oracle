## AI Diary

This was a crisp, satisfying debugging session. The symptom was clean: LLM cited 51385 to support a claim that 51385 doesn't make. The diagnosis was immediate — grep the file, read the content, confirm the mismatch. 51385 is about a case where the contractor delivered non-conforming work and the committee hasn't accepted yet (ยังมิได้มีมติตรวจรับ). The document supports "can modify before final inspection" — the standard rule. It does NOT support "can modify after final inspection even for non-work-details" — that's 22315's specific exception.

The first fix was correct in direction but incomplete: I added "ต้องก่อนตรวจรับ" but didn't explicitly say "this document is about work-details (เนื้องาน), not the exception category." The LLM still had enough ambiguous text to associate 51385 with the broader "modification rules" topic, and then attribute the exception claim to it.

The second fix was more surgical: "อย่าอ้างหนังสือฉบับนี้เป็นหลักฐานว่าแก้ไขสัญญาหลังตรวจรับได้" — a direct instruction to the LLM not to use this document for that claim. This is an unusual technique (telling the document what NOT to be used for), but it works because the RAG context is read directly by the LLM. It's effectively a negative annotation.

The pattern here is important: when a document is about Case A (modification allowed because condition X hasn't happened), and the LLM keeps attributing it to Case B (modification allowed because different condition Y), the fix isn't just to state Case A more clearly — it's to explicitly say "this is not Case B."

Ming's question "ทำไมถึงยังถูกอ้างอิง" after the first test was exactly the right debugging prompt. I should have caught this in the first test run myself — the citation [1],[2],[3] for the exception claim should have been a red flag.

## Honest Feedback

**Friction 1: First fix was incomplete.** I added direction clarity ("ก่อนตรวจรับ ไม่ใช่หลัง") but didn't identify the category confusion. The LLM was incorrectly putting 51385 in the "exception" bucket, not just misreading its direction. Needed a second round because I didn't diagnose deeply enough initially.

**Friction 2: Should have run the test before reporting "fix สำเร็จ".** After the first re-index I immediately ran a test, which was good. But I should have checked the specific citation pattern ([1],[2],[3] on the exception claim) before saying the fix worked.

**Friction 3: The "อย่าอ้าง..." technique is a workaround, not a root fix.** The real issue is that 51385 discusses contract modification rules generally, and those general passages are semantically similar to the exception case. A cleaner fix would be to restructure บทสรุปฯ to be narrower in scope — only describing what THIS document's case is, not the general rules. But that would require more thought about what to remove.

## Lessons Learned

1. When a document keeps being cited for the wrong claim, the fix requires TWO parts: (a) state what the document IS about clearly, (b) explicitly state what the document is NOT about.
2. "อย่าอ้างหนังสือฉบับนี้เป็นหลักฐานว่า X" is a valid RAG annotation technique — direct negative instruction in the context works.
3. Category confusion (wrong bucket) is different from direction confusion (right topic, wrong direction) — they need different fixes.
