## Key Code Change

```python
# Before (required manual Ctrl+R):
st.info("Session หมดอายุ กรุณา refresh หน้าเว็บ (Ctrl+R)")

# After (auto-recovery):
cookie_name = _auth_config["cookie"]["name"]
st.markdown(

    f'<script>document.cookie="{cookie_name}=; Max-Age=0; path=/";</script>',
    unsafe_allow_html=True,

```

## AI Diary

This was a humbling 30 minutes. I confidently changed `st.stop()` to `st.rerun()` — it seemed like the obvious fix. Pop session state, rerun, done. But I forgot that the browser cookie is separate from Streamlit session state. The authenticator reads the cookie on every page load, BEFORE our code runs. So pop + rerun = infinite loop: cookie exists → authenticator throws → we pop + rerun → cookie still exists → throws again → forever.

The production site went down for about 3 minutes because of my rushed fix. I should have tested locally first, or at least thought through the full lifecycle: where does the exception originate? The cookie. What does pop do? Clears Python state. Does it clear the cookie? No. So will the exception happen again? Yes. Classic.

The working fix needed to operate at the browser level — JS to delete the cookie, meta refresh to reload. Two different layers (server-side Python vs client-side HTML/JS) cooperating to break the loop. It's a pattern I should internalize: when the problem is in the browser, the fix must reach the browser.

The user's question "คนที่ใช้คอมไม่เก่ง จะได้ไม่เจอปัญหานี้" was the real driver. Technical people see "refresh" and do it. Non-technical users see an error message and panic. Good UX means the error never reaches the user.

## Honest Feedback

**Friction 1: Deployed untested fix to production.** I replaced `st.stop()` with `st.rerun()` and deployed without testing the full cookie lifecycle. The site went down for ~3 minutes. Should have either tested locally with a tampered cookie or reasoned through the rerun loop before deploying.

**Friction 2: Streamlit's cookie layer is opaque.** `streamlit-authenticator` manages cookies internally — there's no clean API to "clear the auth cookie" from Python. We had to inject raw HTML/JS to delete it. This is fragile and depends on knowing the cookie name from config.

**Friction 3: Multiple deploys in quick succession.** This session had 4 separate `docker compose build + up` cycles in 30 minutes. Each rebuild takes time and each deploy risks the site being briefly unavailable. A staging environment or local Docker test would catch issues before production.

## Lessons Learned

1. **`st.rerun()` without clearing the browser cookie = infinite loop** — Streamlit session state and browser cookies are separate layers. The authenticator reads the cookie first, before session state matters. Must delete the cookie at the browser level (JS) before any rerun/refresh.
2. **When the bug is in the browser, the fix must reach the browser** — Python-side `pop()` can't clear a browser cookie. Use `st.markdown(unsafe_allow_html=True)` with `<script>` to operate at the client level.
