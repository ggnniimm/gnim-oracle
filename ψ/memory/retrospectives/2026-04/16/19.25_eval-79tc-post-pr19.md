## Honest Feedback

**Friction 1: I didn't tell Ming upfront that eval takes ~8 min.** I launched with no time estimate. When it was still running at 9 min, Ming had no baseline to know if this was normal or stuck. I should have said "typical: 8 min; I'll check every ~5" at launch. Ming shouldn't have to guess the expected duration from my check cadence.

**Friction 2: The 568-line eval log is mostly retry noise.** Readers (me, future sessions) have to grep past ~160 retry lines to see TC results. The eval's verbose logging is fine for normal runs but pathological during Gemini outages. Worth adding a `--quiet-retries` flag or downgrading routine retry logs to DEBUG level. Recorded as a followup, not fixed here.

**Friction 3: I treated exit code 1 as "failed" initially.** The background task notification said `<status>failed</status>` because of the exit code. That's misleading — eval exits 1 whenever any TC fails, even if 76/79 is healthy. I shouldn't have needed a second read of the output to realize this. Could add `--summary-only-exit-0` but the quicker lesson is: always read the output, not the exit code, for test suites.

## Lessons Learned

1. **Eval exit code ≠ success signal for test suites** — 76/79 passed is a healthy number, but the process exits 1 anyway. Always check the SUMMARY section before reacting to exit status.
2. **Gemini 503s don't generalize from eval to production** — eval bursts 79 req in 5 min, production sparses them across hours. The retry/fallback chain masks the congestion from real users. Don't extrapolate eval pain to user pain.
3. **One failing TC run is variance, not regression** — 2026-03-14 learning held up today. Before claiming PR #19 regressed TC-027/TC-037, need a second run after Gemini infra recovers. Resist the urge to "fix" based on single data points.
