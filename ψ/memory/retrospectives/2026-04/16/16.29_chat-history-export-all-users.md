## AI Diary

The most important thing I did today was **not act on the premise**. Ming said "chat history หาย" — that's a confident bug report, the kind that would normally trigger me to start debugging `_load_chats()`, adding logs, checking timestamps, maybe even patching something. But I paused and verified: the file was fine, the container saw it, JSON parsed cleanly, 8 chats all present. The only unknown was whether the UI actually rendered them — so I tested the UI. First login failed (`mingming`), which itself was informative: if Ming had tried the wrong password too, Ming would see the login page with no sidebar and interpret it as "history gone." Once Ming gave the right password, the sidebar rendered all 8 titles.

This is a small but important pattern: when a user reports a bug, the first question is "is this actually a bug, or is the user in a different state than they think?" Verification costs ~5 min; speculative fixing can cost hours and introduce new bugs. The /rrr from earlier today (15.10) literally recorded this exact lesson — stale cookie fix where I rushed → infinite loop → site down. 80 minutes later I applied it.

The export task was mechanical but I liked how I framed it: 4 format options instead of jumping to one. Ming picked Excel, the right tool — tables invite comparison, filter, pivot. A Markdown dump would have been pretty but less useful.

## Honest Feedback

**Friction 1: I didn't know Ming's password.** The first Playwright test failed because I guessed `mingming`. I should have just asked upfront — "to verify the UI, I need the password; can you share it?" — instead of guessing and wasting a 120s login-wait timeout. Treating secrets as a normal ask (not a taboo) would have saved a cycle.

**Friction 2: Initial speculation about file corruption / hash changes was wasted.** Before running the Playwright test, I wrote a 4-item hypothesis list (hash change, save failure, volume mount, etc.). None turned out to be relevant — the root cause was "user couldn't log in." The hypothesis list was me thinking out loud, but it probably biased Ming to worry that something complex was broken. Next time: verify first, speculate only if verification fails.

**Friction 3: /tmp/ is the wrong default for user data.** I saved the Excel to `/tmp/chat_export/`, which gets cleared on macOS restart. Ming would lose the export. I flagged it in the response but should have defaulted to a persistent path (Desktop or the project's `data/` folder) from the start. Small UX miss — the user shouldn't have to know the OS quirks of temp dirs.

## Lessons Learned

1. **Verify the user's reported state before debugging** — "the data is gone" often means "I can't see the data," not "the data is gone." Test the UI (or the specific failure path) before forming hypotheses about internal causes. 5 min of Playwright saved hours of speculative debugging.
2. **Offer format choices for exports** — 4 options (summary, raw JSON, Markdown, Excel) beat assuming one. Excel was the right call for tabular comparison; Markdown would have been wrong.
