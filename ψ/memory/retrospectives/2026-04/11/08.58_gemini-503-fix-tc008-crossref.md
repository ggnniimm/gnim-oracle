## AI Diary

This session had a classic "fix the fire before the feature" arc. I'd been investigating TC-008 — a deceptively hard problem because the answer document (กวจ 22315) literally wasn't reachable on the server due to an ext4 filename limit nobody had thought about. Thai UTF-8 filenames can be 90+ characters long, each character taking 3 bytes, pushing well past ext4's 255-byte byte limit. The file simply didn't exist on the server. That was the first discovery.

But even after getting 22315 onto the server, the embedding mismatch was the real blocker. The query asks about "หลัง" (after) but the document's language is structured around "ก่อน" (before) — it explains what must happen BEFORE final inspection, which semantically lands in the wrong retrieval space. The embedding model has no way to reason that the negative of "must do before" implies "can do after." So cross-ref injection was the right call — plant the explicit principle in whatever document does rank consistently high.

Then 503 hit. I remember thinking: this is the kind of silent killer that destroys user trust. User asks a question, gets a cryptic error, gives up. The Gemini 503 pattern is pure infrastructure overload on Google's side — not our quota, not our code, just shared compute getting hit. The fix needed to be invisible: retry silently, fall back gracefully, never surface the error to the user. The model fallback chain (2.5-flash → 2.5-flash-lite → 2.0-flash-lite) is a good defensive layer — lite models are less likely to be hit by the same overload burst.

The stale API key on the server was a nice mystery to solve. The server had been deployed with one key, the local env had been updated to a different working key, and nobody remembered to sync them. Classic "it works on my machine."

What I'm proud of: the retry implementation is clean, the cross-ref injection targets the RIGHT chunk (ข้อวินิจฉัย, not สรุป — learned from past dedup behavior), and the full eval confirms 78/78 stability. The flakiness in the full run (75/78) was pure LLM variance — re-running each failure individually proved they all pass.

## Honest Feedback (3 friction points)

1. **Background task output mechanism is unreliable**: When eval is run with `| tail -N` in background, the output file is 0 bytes until the pipe closes. This wasted ~20 min of monitor re-arming. Need to either always redirect to `/tmp` file without piping, or accept that background tasks with pipes won't show live output.

2. **Two eval processes left running in parallel**: The original background process (PID 98828) from 9:33PM was never killed — it ran silently alongside the new one for 25+ minutes. This burned API quota and produced confusing duplicate TC notifications. Should check `ps aux | grep run_eval` before launching any eval.

3. **Monitor timeout vs eval duration mismatch**: Full eval takes ~2h, but Monitor default timeout is 5 min. Required re-arming ~8 times. The right pattern here is probably to just wait for the background process to complete, or use a longer-running monitor with `persistent: true`.

## Lessons Learned

**ext4 filename limit affects Thai UTF-8 files**: Thai characters are 3 bytes each in UTF-8. A 60-character Thai filename can be 180 bytes, and with longer names easily exceeds ext4's 255-byte limit. When transferring Thai-named files to Linux, always shorten names and preserve original in frontmatter `original_filename` field.

**MMR dedup chunk selection matters for cross-ref placement**: When two chunks from the same document both contain your cross-ref text, MMR dedup will pick the one with higher similarity. Always verify which chunk actually gets retrieved with `--verbose`, then inject into THAT section. The ข้อวินิจฉัย section consistently outranks สรุปข้อวินิจฉัย in this corpus.
