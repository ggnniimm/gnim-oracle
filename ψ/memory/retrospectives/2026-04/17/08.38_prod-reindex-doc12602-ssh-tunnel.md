## AI Diary

This was a short session but it had three failure modes stacked on each other, each reasonable to hit. Port 22 blocked by Wi-Fi (known gotcha, documented in memory). Host Python missing tqdm (obvious in hindsight — host has no deps, only Docker does). Qdrant not exposed on host (correct security posture, not a bug). SSH tunnel failing because of the above. Each failure was logical but I hit them in sequence instead of anticipating them.

The thing that worked — `python-crfsuite` as the pip package name for `pycrfsuite` — I'm not proud I had to try it. The two packages (`pycrfsuite` and `python-crfsuite`) are basically the same library with different distribution names depending on the platform and Python version. `pycrfsuite` installs fine on x86-64 with Python 3.10 (our local Mac setup) but not on the server. `python-crfsuite` is the Cython-free pure-wheel alternative that works on more platforms. I should have known this and tried it first.

The bigger concern I'm sitting with: `python-crfsuite` installed inside the container is ephemeral. If the container is rebuilt (which it will be, next time we `docker compose build app`), the library is gone and the same pipeline error will hit again. The right fix is to add `python-crfsuite` to `requirements.txt` in the project. I didn't do that. I got the immediate fix done but left a latent fragility. Ming didn't ask me to persist it and I didn't flag it proactively. That's a gap.

## Honest Feedback

**Friction 1: I tried SSH tunnel before checking if Qdrant is exposed on host.** The tunnel requires a listening port on the server's localhost. I should have checked `docker inspect` port bindings before setting up the tunnel. Checking first would have saved a failed tunnel attempt and the "connection reset" error that looks like a network problem.

**Friction 2: I didn't flag the ephemeral pip install risk proactively.** `pip install` inside a running container is temporary — it disappears on container rebuild. I completed the task without mentioning this. Ming may not know that a future `docker compose build app` will break the pipeline again. Should have said: "fix works now, but `python-crfsuite` is not in requirements.txt — next rebuild will lose it."

**Friction 3: I didn't try `python-crfsuite` first.** `pycrfsuite` vs `python-crfsuite` is a known platform-split. I tried `pycrfsuite` first (failed), then eventually found `python-crfsuite`. Should have tried both in one step or known the alternative immediately.

## Lessons Learned

1. **`python-crfsuite` is the pip-installable alternative to `pycrfsuite` on platforms where the C extension doesn't build** — when `pip install pycrfsuite` fails with "no matching distribution," try `python-crfsuite` instead. Same library, different PyPI distribution.
2. **pip install inside Docker container is ephemeral** — always follow up by adding the package to `requirements.txt` (and rebuilding the image) if the dependency is needed long-term. Flag this to the user immediately when doing ephemeral installs.
3. **Check Qdrant port bindings before SSH tunnel** — `docker inspect <container> --format "{{json .HostConfig.PortBindings}}"` confirms whether the port is reachable from host. Empty `{}` = not exposed, tunnel will fail.
